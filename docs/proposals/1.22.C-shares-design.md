# 1.22.C design proposal — `aa:Share` + access control

**Status:** HISTORICAL — implemented and shipped (1.22.C); retained as design record.
**Scope:** the load-bearing security layer for federation. Decides what content flows between paired peers.
**Sequence:** ships AFTER 1.22.B-cleanup (done, commit `526ca83`); BEFORE 1.22.D (inbox/outbox/delivery worker).
**Authoritative references:** ADR 0043 (federation strategy), ADR 0044 (activities ledger / transactional emit), `docs/spec/federation/v1.md`.

---

## 0. Invariants this proposal is trying to preserve

1. **Pairing alone shares no content.** Per ADR 0043 §"Trust model" — every shared object is an explicit, separate opt-in. This is the central invariant the entire walled-garden design hangs on.
2. **No tier auto-fans content to every paired peer.** This kills the Mastodon-style "follow = subscribe to everything" failure mode.
3. **Trust establishment goes through the handshake (1.22.B-b).** Sharing is a separate, per-object decision.
4. **The activity is the source of truth.** Per ADR 0044, every social action emits an activity row in the same transaction as the domain write. Shares are no different — `aa:Share` and `aa:Unshare` activities are the canonical record; `federation_shares` rows are a projection optimized for the gate-check hot path.
5. **Write-ahead audit.** Per the reviewer's checklist: the audit row commits BEFORE the share takes effect. Failures during share processing must NEVER leave a state where content flows but no audit row records the grant.

---

## 1. Four visibility tiers

Five tiers were considered in the prior framing. The `connected-peers` tier was dropped — it structurally re-introduces "pairing = sharing" which ADR 0043 was written to prevent.

| Tier | Federation? | Per-recipient gate | Stored as |
|---|---|---|---|
| **private** | No | n/a — author + local admins only | `visibility='private'` on the object |
| **org-only** | No | local team/role ACL | `visibility='org-only'` + existing ACL tables |
| **followers** | Yes | `Accept(Follow)` per user — explicit consent at the follower side | `visibility='followers'` + `federation_shares` rows with `object_kind='user'` (the followers ARE the share rows) |
| **explicit-share** | Yes | `federation_shares` row per recipient required | `visibility='explicit-share'` + per-recipient `federation_shares` rows |
| **public** | Yes (opt-in only) | none — anyone can read | `visibility='public'`, AND a `system_config.federation_public_enabled = true` operator toggle. Default OFF. |

### Why "followers" via `Accept(Follow)` is correct

`Accept(Follow)` is the load-bearing consent step. A peer's user sent us a `Follow`, our user clicked "Accept" — that IS the per-recipient opt-in. Once accepted, a `federation_shares` row exists with `object_kind='user'`, `object_id=<our user's actor>`, `target_user_url=<the follower's actor URL>`, `scope='view'`, `expires_at=NULL`.

Then "publish a post with followers visibility" becomes: look up every share row for the author with `object_kind='user'` → deliver the post to each. No separate followers table. Follow / Unfollow is share-row insert / delete.

### Why "public" is opt-in twice

Once at the object level (`visibility='public'`) AND once at the instance level (`system_config.federation_public_enabled`). The instance-level toggle defaults OFF. Walled-garden installs never enable it. If a future operator opts into the public-fediverse interop, posts already marked `public` start flowing — but until then, even a `public` post stays inside the walled garden (treated as `followers` for delivery purposes; only locally visible without follower-of for read).

## 2. Schema

### 2.1. The visibility enum on each shareable object

Every shareable object's domain table gets a `visibility` column with CHECK against the four-tier closed catalogue. Posts already have one; collections / workspaces / brand_kits need one added (migrations + handler validation).

```sql
visibility TEXT NOT NULL DEFAULT 'private'
    CHECK (visibility IN ('private', 'org-only', 'followers', 'explicit-share', 'public'));
```

Typed Go constants in `federation.ObjectVisibility` per ADR 0042.

### 2.2. `federation_shares` table

```sql
CREATE TABLE federation_shares (
    id                  UUID         PRIMARY KEY DEFAULT gen_random_uuid(),

    -- WHO is granting access (this instance's user).
    -- Local user_ref so a deleted-user cascade cleans up; their
    -- actor URI is derivable from username at delivery time.
    grantor_user_ref    BIGINT       NOT NULL,

    -- WHAT is being shared.
    object_kind         TEXT         NOT NULL
        CHECK (object_kind IN ('asset', 'post', 'collection',
                                'workspace', 'brand_kit', 'user')),
    object_id           UUID         NOT NULL,

    -- WHERE it's going.
    -- peer_id is the FK to federation_peers. ON DELETE CASCADE so
    -- defederation auto-purges shares with that peer.
    peer_id             UUID         NOT NULL
        REFERENCES federation_peers(id) ON DELETE CASCADE,

    -- target_user_url:
    --   NULL = any user on that peer (broadcast within the peer)
    --   non-null = specific user (actor URL at the peer)
    target_user_url     TEXT         NULL,

    -- HOW MUCH access.
    scope               TEXT         NOT NULL DEFAULT 'view'
        CHECK (scope IN ('view', 'comment', 'annotate', 'remix')),

    -- WHEN it expires (NULL = no expiry).
    expires_at          TIMESTAMPTZ  NULL,

    -- WHY (operator note + correlation back to the originating
    -- aa:Share activity).
    notes               TEXT         NOT NULL DEFAULT '',
    granted_activity_id UUID         NOT NULL
        REFERENCES activities(id) ON DELETE RESTRICT,

    -- BOOKKEEPING.
    granted_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    revoked_at          TIMESTAMPTZ  NULL,
    revoked_activity_id UUID         NULL
        REFERENCES activities(id) ON DELETE RESTRICT,

    -- Uniqueness: at most one ACTIVE share per
    -- (grantor, object, peer, target_user). A revoked row
    -- (revoked_at IS NOT NULL) doesn't collide.
    -- Implemented via partial unique index, not a column-level
    -- UNIQUE, so the revoked rows can stay for audit.
);

CREATE UNIQUE INDEX federation_shares_active_uniq_idx
    ON federation_shares (grantor_user_ref, object_kind, object_id, peer_id, COALESCE(target_user_url, ''))
    WHERE revoked_at IS NULL;

-- Hot read #1: inbox filter. Every inbound activity checks:
--   "is there an active share row for (object, requesting peer, requesting user)?"
CREATE INDEX federation_shares_lookup_idx
    ON federation_shares (object_kind, object_id, peer_id)
    WHERE revoked_at IS NULL;

-- Hot read #2: outbox dispatch. For a new activity about object X,
-- iterate every active share row to know who to deliver to.
CREATE INDEX federation_shares_delivery_idx
    ON federation_shares (object_kind, object_id)
    WHERE revoked_at IS NULL;

-- Hot read #3: defederation cascade preview. Count shares per peer
-- so the admin UI can show "you'll unshare N objects".
CREATE INDEX federation_shares_by_peer_idx
    ON federation_shares (peer_id)
    WHERE revoked_at IS NULL;
```

### 2.3. Three new activity types

Per ADR 0043 §"Custom activity types": `aa:Share` already exists in the catalogue (`federation.ActivityAAShare`). `aa:Unshare` already exists. New addition: `aa:RevokeShare` — distinct from `aa:Unshare` because:

- `aa:Unshare` = "stop sharing this object with this recipient" (admin-initiated, normal lifecycle)
- `aa:RevokeShare` = "the share was rescinded by an authority — moderator override, abuse response" (admin-initiated with reason; audit-marked differently)

Both write `revoked_at` + emit a Delete-shaped activity. The differentiation is for audit + future moderation tooling; the wire behavior is the same.

## 3. Containment semantics

### 3.1. Collection-as-container

Sharing a Collection grants the scope on every asset CURRENTLY in the collection, transitively.

> **Amended by #893.** As originally written and implemented, this had no constraint on
> who owns the member — the grant check protected the container and nothing re-checked
> the contents, so a collection owner could confer peer scope over an asset that was
> never theirs to share. The implicit grant is now bounded: it reaches a member only if
> the SHARE'S GRANTOR could have shared that member directly — they own it, or they hold
> `system.admin`, which is the same pair of conditions §5 of this document requires on
> the grant path. Members with no resolvable local owner (federated mirrors, system
> imports) are refused. The bound is evaluated per member at check time and is
> deliberately NOT cached: the per-object share snapshot holds share rows, and a
> membership or ownership change writes no share row, so folding the answer in would
> leave the cache serving a stale grant.

- The `federation_shares` row for the Collection drives an implicit grant on every asset in `collection_resources` **whose owner the grantor could have shared it on behalf of** (#893).
- Implicit grants are NOT materialized as separate rows. The inbox filter resolves them at check time via a JOIN: "does this asset belong to a collection that's shared?".
- New assets added to a shared collection are AUTOMATICALLY covered by the existing share — subject to the #893 bound above — with no extra share row and no new aa:Share activity. (BUT: an `aa:Add` activity to the collection IS emitted per 1.22.A-bis-4, and federated peers know to extend their local view.)

### 3.2. Workspace-as-container

Sharing a Workspace grants the scope on every child collection AND every brand_kit in the workspace, transitively. (Still unimplemented — the `workspaces` table does not exist. When it lands it takes the same #893 member-ownership bound as §3.1.)

- Same materialization rule: NO synthetic rows. Resolved at check time via two-hop JOIN.
- A workspace share automatically covers new child collections; child shares are NOT auto-created.

### 3.3. The "two different decisions" rule

**Unsharing a parent does NOT remove explicit shares previously granted directly on its children.**

Example: share Workspace W with Peer P. This covers Collection C (a child of W) implicitly. Later, separately, share Collection C explicitly with Peer P (perhaps with a different scope — say `annotate` vs the workspace's `view`).

Now revoke the workspace share. The collection share IS NOT removed — it was a separate decision.

The implementation: the inbox filter checks `(object_kind, object_id, peer)` directly first, falls back to container-based checks. Container-based access vanishes when the container is unshared; direct grants persist.

### 3.4. Containment is read-time only

We deliberately avoid materializing transitive shares. The cost is per-check JOIN; the benefit is no fan-out write storm when a 10,000-asset collection is shared. The JOIN is bounded (collection_resources is indexed by collection_id; workspace_collections by workspace_id; both small per-collection in practice).

## 4. Revocation

### 4.1. The unshare lifecycle

1. Admin clicks "unshare" on the share UI.
2. Server: `aa:Unshare` activity emitted via `WithEmission` (atomic with the share write).
3. Same tx: update `federation_shares` set `revoked_at = NOW()`, `revoked_activity_id = <new activity uuid>`.
4. Tx commits. Audit row already written-ahead at activity emit (see §6).
5. Post-commit: outbox dispatcher (1.22.D) delivers the `aa:Unshare` envelope to the affected peer's inbox endpoint. Recipient is expected to purge local caches of the object.

### 4.2. What the recipient does

Per the spec, on receiving `aa:Unshare(object=X, target=local user)`:
- Drop any cached copy of X from local storage.
- Recipient user's UI shows X as "access revoked" instead of the content.

### 4.3. What the recipient KEEPS

Recipient's own annotations / comments / derivative work on X are NOT deleted. Those are the recipient's data. They retain the metadata + their own contributions; they lose access to the underlying asset bytes / post body.

This is a deliberate choice: the recipient may have spent hours commenting on a shared design doc. We don't punish them by deleting their work when access is revoked. They get a "the underlying asset was revoked by the grantor" placeholder, but their comments remain in their own collection.

### 4.4. Defederation cascade

Defederating a peer (DELETE on `federation_peers`):
- FK CASCADE drops every `federation_shares` row pointing at that peer.
- BEFORE the delete commits: a final `aa:Unshare` activity is emitted per shared object to the peer's inbox (best-effort delivery via the outbox).
- Admin UI shows a cascade-preview modal BEFORE the delete: "Defederating Studio B will:
  - Revoke 47 shares
  - Cancel 3 pending handshake invitations
  - Drop 12 cached suggestions
  - Send a final aa:Unshare for each revoked share (best-effort).
  Continue?"

This cascade-preview is implemented as a new endpoint `GET /admin/federation/peers/{id}/defederation-preview` that returns the impact summary. The DELETE itself then runs the cascade.

## 5. Inbox filter

### 5.1. The decision function

```
canPeerAccessObject(peer_id, user_url, object_kind, object_id, required_scope) → bool
```

Returns true iff there exists an active `federation_shares` row where:
1. `object_kind` matches AND `object_id` matches (direct grant), OR
2. `object_kind = 'collection'` AND `object_id` is the collection containing the requested asset (container grant), OR
3. `object_kind = 'workspace'` AND `object_id` is the workspace containing the requested asset / collection (two-hop container grant)

AND for each candidate row:
- `peer_id` matches the requesting peer
- `target_user_url` is NULL (broadcast within peer) OR matches the requesting user
- `revoked_at IS NULL`
- `expires_at IS NULL` OR in the future
- `scope >= required_scope` (ordering: view < comment < annotate < remix)

### 5.2. Where the gate fires

Every inbound activity that targets an object passes through `canPeerAccessObject` at the dispatch layer (1.22.D inbox). Three outcomes:

| Outcome | Action |
|---|---|
| **Allowed** | Activity dispatched to the relevant handler (Like, Comment, etc.) |
| **Rejected** | Activity DROPPED (no domain write) + `federation.activity.rejected` audit event emitted with the reason |
| **Error** | DB failure during the check; the activity is requeued for retry with backoff (per the inbox queue design in 1.22.D) |

### 5.3. The reason taxonomy

`federation.activity.rejected` events carry a `reason` field with a closed enum:
- `no_share_row` — no active share for this object × peer pair
- `wrong_user` — share exists but `target_user_url` doesn't match requester
- `expired` — share's `expires_at` is in the past
- `revoked` — share's `revoked_at` is set
- `insufficient_scope` — share grants `view` but action requires `comment`/`annotate`/`remix`
- `peer_disabled` — `federation_peers.enabled = false`
- `peer_not_connected` — `federation_peers.status != 'connected'`
- `grantor_not_owner` — a container share covering the object exists and matches peer/user/scope, but its grantor neither owns the object nor holds `system.admin`, so it confers nothing on it (#893). The most specific reason in the taxonomy: it distinguishes "the grant was never the grantor's to make" from "there is no grant".

### 5.4. Activity-to-scope mapping

| Activity verb | Minimum required scope |
|---|---|
| `Like` | view |
| `Announce` (repost) | view |
| `Create(Note)` (comment) | comment |
| `aa:Annotation` (whiteboard / text annotation) | annotate |
| `aa:WorkflowTransition` (move asset through workflow) | remix (highest — implies write authority on the object) |
| `Create(Post)` derived-work | remix |
| `Delete` of own derivative work | view (deleting your own stuff doesn't need write scope on the original) |

## 6. Encryption tier interaction

### 6.1. The two orthogonal axes

Per ADR 0043:
- **Visibility tier** (this proposal): WHO can access
- **Encryption policy** (federation_peers): HOW the bytes are protected in transit + at rest on the peer

Restricted / embargo content (a per-asset metadata flag) ALWAYS rides in a NaCl-box envelope, regardless of the peer's encryption_policy. The policy determines whether NON-restricted content also gets envelopes.

### 6.2. The recipient-key resolution

The `federation_shares` row does NOT carry a recipient public key directly. Instead, at delivery time:
- For `target_user_url = NULL` (broadcast within peer): no encryption envelope possible. Restricted content can NEVER be broadcast — sharing restricted content requires `target_user_url` set. The share-form UI enforces this client-side; the server enforces it on share creation (returns 400 "restricted objects require a target user").
- For `target_user_url = <specific user>`: at delivery time, the outbox dispatcher fetches the target user's actor doc (`GET <target_user_url>`), extracts the X25519 encryption pubkey from the doc, and wraps the payload via NaCl-box per ADR 0020 + v1.md §6.5.

### 6.3. Wrapping atomicity

Wrapping happens at delivery time, NOT at share creation time. Reason: the recipient user might rotate their key between share-grant and an activity-about-the-object. The activity is wrapped fresh per delivery with the recipient's then-current key.

The activity row itself stores the plain payload + the share_id it was filtered through. The outbox does the wrap. This keeps the activities table introspectable to the GRANTOR's admin (who has authority over their own data) while preserving end-to-end encryption to the recipient.

## 7. Audit events

### 7.1. The three new event types

| Event type | When fired | Payload fields |
|---|---|---|
| `federation.share.granted` | `aa:Share` activity commits | actor, object_kind, object_id, peer_id, target_user_url, scope, expires_at, correlation_id |
| `federation.share.revoked` | `aa:Unshare` or `aa:RevokeShare` activity commits | actor, object_kind, object_id, peer_id, target_user_url, share_id, reason, correlation_id |
| `federation.activity.rejected` | inbox filter rejects an inbound activity | source_peer_id, source_user_url, activity_type, object_kind, object_id, reason (from §5.3 taxonomy), correlation_id |

### 7.2. Write-ahead-audit invariant

**The audit row commits BEFORE the share takes effect, not after.**

Implementation: the share write is wrapped via `activities.WithEmission`. The emit helper for `aa:Share` returns an Emission with BOTH the activity record AND an audit-event record. WithEmission writes both in the same transaction as the domain write. If anything fails, the whole tx rolls back — share never takes effect, audit row never appears.

This is the load-bearing safety property. We never end up in a state where:
- The share row exists but no audit row records who granted it (would mask abuse)
- The audit row exists but no share row was created (would falsely report a grant that never happened)

### 7.3. Correlation IDs

Every audit event carries a `correlation_id` matching the originating activity's UUID. The audit view can pivot on correlation_id to see "this share-grant audit event, the resulting share-row, the eventual revocation audit, the final unshare delivery" as one chain.

Implementation lands AFTER the backend in 1.22.C; this section sketches the screens.

### 8.1. Per-object share dialog

Opened from a "Share with peers" button on the post / collection / workspace / brand kit detail view. Shows:
- Current shares (recipient list + scope + expiry per row)
- "Add recipient" form: peer dropdown + user picker (or "any user on this peer") + scope dropdown + optional expiry datepicker
- Revoke button per existing share

### 8.2. Per-peer outbound view

`/admin/federation/peers/{id}/shared` — "what am I sharing with this peer?"
- Grouped by object kind
- Each share with scope + recipient + expiry + Revoke button

### 8.3. Per-peer inbound view

`/admin/federation/peers/{id}/received` — "what is this peer sharing with me?"
- Same shape but read-only (we can't unilaterally revoke a share the grantor controls)
- "Drop from local cache" button (recipient-side; doesn't affect grantor's share row)

### 8.4. Per-object "who has access?" view

On the object's detail page (post / collection / etc.) — admin-only — shows:
- Visibility tier of the object
- Every share row touching this object (direct + via container)
- Last access time per recipient (if we surface it — TBD)

## 9. Five worked examples

### 9.1. Share a collection

**Actor:** Alice on instance A, sharing collection "Concept Sketches" (3 assets) with Bob on instance B at `view` scope.

1. Alice opens the collection, clicks "Share with peers". Selects Studio B + Bob + scope=view.
2. Frontend POST `/collections/{id}/shares` → handler validates: Alice owns collection; Studio B is connected+enabled; Bob's URL is well-formed.
3. Handler calls `WithEmission`:
   - `aa:Share` activity row inserted (actor=Alice, object=collection X, target=Bob@B, scope=view)
   - `federation_shares` row inserted with `granted_activity_id` = the new activity's UUID
   - Audit event `federation.share.granted` written
   - All in one tx. Commits.
4. Outbox dispatcher (1.22.D) picks up the `aa:Share` activity, delivers to `https://B/federation/inbox`.
5. Instance B's inbox accepts the envelope (peer is connected; activity_type is `aa:Share`).
6. Instance B persists a "shared with me" record locally for Bob; Bob's UI now shows the collection.

**Implicit grant:** the 3 assets in the collection are now accessible to Bob via container resolution. No extra share rows.

### 9.2. Unshare a collection

**Actor:** Alice deciding to revoke Bob's access to "Concept Sketches".

1. Alice opens the share UI for the collection, clicks Revoke on Bob's row.
2. Handler calls `WithEmission`:
   - `aa:Unshare` activity row inserted (actor=Alice, object=collection X, target=Bob@B)
   - `federation_shares` row updated: `revoked_at = NOW()`, `revoked_activity_id` = new activity UUID
   - Audit event `federation.share.revoked` written (reason=user_revoked)
   - All in one tx.
3. Outbox dispatcher delivers `aa:Unshare` to Studio B's inbox.
4. Studio B drops cached collection + assets from Bob's view.
5. Bob's UI now shows "Access revoked by Alice@A".
6. If Bob had added comments on any of the assets, those comments remain in Bob's personal history — only the underlying assets become inaccessible.

### 9.3. Follow a user

**Actor:** Bob on instance B following Alice on instance A.

1. Bob clicks "Follow" on Alice's profile in B's UI.
2. B's handler emits a `Follow` activity to A's inbox.
3. A's inbox dispatcher gates `Follow` differently from `Like` / `Comment` — it doesn't require a `federation_shares` row to ACCEPT (Follow is a request, not access).
4. A's handler: creates a pending follow request in A's domain table; surfaces it in Alice's notification feed.
5. Alice clicks "Accept" on the request.
6. A's handler calls `WithEmission`:
   - `Accept(Follow)` activity emitted to B's inbox
   - `federation_shares` row inserted: `object_kind='user'`, `object_id=Alice's user UUID`, `peer_id=B's peer row`, `target_user_url=Bob's actor URL`, `scope='view'`, `expires_at=NULL`
   - Audit event `federation.share.granted` (reason=accept_follow)
7. When Alice publishes a `followers` post, the outbox dispatcher iterates all share rows with `object_kind='user'` AND `object_id=Alice's UUID` to find delivery targets. Bob's row matches → post delivered to B.

**Key property:** no separate `user_follows` table for federated relationships. Follower-ness IS share-ness with `object_kind='user'`.

### 9.4. Embargo expiry

**Actor:** Alice sharing an asset with Bob, embargo until a future date.

1. Alice shares asset X with Bob, `scope=view`, `expires_at='2026-12-31T00:00:00Z'`.
2. `federation_shares` row written with the expiry. `aa:Share` activity emitted normally.
3. Between now and expiry: every `Like` / `Comment` from Bob on X passes the inbox filter (scope sufficient, not expired, not revoked).
4. At expiry: NO active expiry-sweep job is needed. The inbox filter (§5.1) checks `expires_at IS NULL OR > NOW()` per request. As soon as NOW() crosses the expiry, all new activities about X from Bob are rejected with `reason='expired'`.
5. BUT: the cached asset on B's side is still there. To force B to purge, an OPTIONAL background job ("expiry sweeper") emits `aa:Unshare` activities for shares that expired in the last hour. This is best-effort housekeeping — the inbox filter is the load-bearing check.
6. Audit log shows: `federation.share.granted` at grant time, then per-rejection `federation.activity.rejected` events with `reason=expired` for any post-expiry activity attempt.

### 9.5. Peer defederation cascade

**Actor:** Alice defederating Studio B (perhaps a ToS violation).

1. Alice opens `/admin/federation/peers/{B.id}`, clicks "Defederate".
2. Frontend GET `/admin/federation/peers/{B.id}/defederation-preview` first — shows the cascade modal (§8.5) with the count summary.
3. Alice confirms.
4. Handler:
   - Reads ALL active share rows for peer B.
   - For each: emit `aa:Unshare` activity (best-effort delivery via outbox).
   - Audit event `federation.share.revoked` per row (reason=peer_defederated).
   - All these activities + audit rows in ONE big transaction (or chunked transactions if N > 1000).
   - Then DELETE the `federation_peers` row → FK CASCADE wipes the share rows + cached suggestions + pending handshakes.
   - Final audit event: `federation.peer.defederated` with the impact summary captured.
5. Outbox dispatcher attempts the delivery of every queued `aa:Unshare`. Some may fail (peer instance unreachable, expected on a hostile defederation). That's fine — the local cleanup is authoritative; the peer-side cleanup is best-effort.
6. Studio B can no longer accept activities from A (their `federation_peers` row for A may also delete it, or they keep it as a connected-but-dead peer until their admin acts).

## 10. What I will NOT do in 1.22.C

- **Cross-instance share negotiation.** Cannot ask the recipient to consent before sharing. Sharing is unilateral on the grantor side; the recipient can drop from cache after the fact but cannot pre-veto. Future possible feature; not v1.
- **Bulk-share UI for "all my Y to peer P".** Each share is per-object. Explicit. Boring.
- **Auto-extending shares on workflow transitions.** A post being approved doesn't auto-share it with anyone new. Visibility changes (e.g., draft → published) are emitted as `Update` activities; the existing shares re-apply per the existing inbox filter.
- **Public-fediverse interop wire format.** Even if `public` tier is enabled, we still emit `aa:Share` shapes, not vanilla ActivityPub. A future translator phase (1.30+) would convert.
- **The full `aa:RevokeShare` distinct flow.** Schema-supports it (the activity type exists in the catalogue), but v1 only ships `aa:Unshare`. Distinct moderation-revoke surface lands when moderation tooling does.

## 12.5. Reviewer answers (locked-in)

Locking in the reviewer's six answers from the design review.

### Scope ladder — confirmed `view < comment < annotate < remix`

Plus a spec clarification on `remix`:

> Remix grants the recipient permission to incorporate the shared
> assets into their own posts, collections, workspaces, or brand
> kits on their own instance. The original asset is never
> modified; new objects reference the shared assets via cas://
> URI. Editing the original requires the recipient be a local
> user on the origin instance.

Future fifth scope `edit` is reserved if cross-instance edit of
the original ever becomes a real ask.

### No last-access-time tracking at v1

The federation_shares table does NOT carry `last_used_at` or
similar. Marginal UX value, real write hot spot. The peer-level
`last_seen_at` on federation_peers covers the "is this peer
alive" question. If operators ask later: add via periodic
sampling (one update per share per day, not per activity).

### `aa:Unshare` only at v1, `aa:RevokeShare` documented for forward-compat

Spec line locked in:

> `aa:RevokeShare` is reserved for future scope-narrowing
> without a gap; v1 implementations MUST treat any inbound
> `aa:RevokeShare` as an `aa:Unshare`.

Scope downgrades in v1: unshare + re-share with narrower scope.
Brief access gap is acceptable.

### Expiry sweeper SHIPS in 1.22.C-d (not optional)

Inbox-filter expiry check handles the gate; sweeper handles the
proactive `aa:Unshare` emission so recipients purge cached bytes.
Without the sweeper, expired-but-unprocessed shares leave the
recipient indefinitely holding bytes they shouldn't have.

Implementation: periodic job via the existing job queue. Each
pass: select expired+active shares, emit `aa:Unshare` per share
via WithEmission, audit event written. Idempotent — re-runs
filter on `revoked_at IS NULL`.

### `public` tier OMITTED from v1 enum

Reserved value. CHECK constraint at v1 covers four tiers:
`private`, `org-only`, `followers`, `explicit-share`. Writes
with `public` are rejected at the API layer with a clear "tier
reserved for future public-fediverse phase" error.

Spec note: implementers MAY recognize `public` for forward-compat
parsing but MUST NOT accept it as a write value at v1.

Adding it back later is a small CHECK migration; cleaner than
maintaining the "treats-as-followers" kludge in the meantime.

### Defederation: chunked at 500 rows per tx, job-queue-driven

Single-tx defederation has pathological behavior at scale (long
lock, big WAL write, audit-event flood). Replaced with:

- Operator-initiated defederation enqueues a
  `federation.peer.defederate` job (existing job queue).
- Job processes shares in 500-row chunks per tx.
- Each chunk: select 500 active shares for the peer, mark
  revoked, emit `aa:Unshare` to outbox, write audit events.
- Admin UI shows progress ("defederating: 1,500 of 5,000
  shares processed").
- Job idempotent + restartable — filter on `revoked_at IS NULL`
  + `peer_id = X`; if worker dies mid-run, next worker picks up.

500 is the chosen number; could be 1,000 with similar properties.
The architectural commitment is "chunked, never single-tx."

The `DELETE FROM federation_peers` row itself happens AFTER the
job completes (so the FK CASCADE on share rows is a no-op — we
already wiped them). This preserves the audit chain: every
revoked share carries a `revoked_activity_id` pointing at a
real `aa:Unshare` row, not a phantom cascade-fired delete.
