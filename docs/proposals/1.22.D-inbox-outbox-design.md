# 1.22.D design proposal — inbox / outbox / delivery worker

**Status:** PROPOSAL — awaiting reviewer approval before implementation lands.
**Scope:** the wire-protocol layer that finally moves data between paired
instances. Bridges everything 1.22.A-C produced (envelopes, signatures,
shares, activities ledger) onto actual HTTP requests.
**Authoritative references:** `docs/spec/federation/v1.md` §§10, 12;
ADR 0043 (federation strategy); 1.22.C design proposal §§3, 4, 5, 6.

---

## 0. Invariants this proposal preserves

1. **Pairing alone shares no content.** The inbox refuses to dispatch any
   inbound activity whose target object lacks a current `federation_shares`
   row (1.22.C-b `CanPeerAccess` is the gate). No bypass.
2. **Idempotent delivery + idempotent receipt.** Both sides retry; both
   sides dedup. A network blip never loses an activity AND never lands one
   twice.
3. **At-rest encrypted recipient bytes when required.** §6.5 of v1.md
   marks restricted objects + e2e-peer policy as MUST-encrypt; the outbox
   wraps with NaCl-box per recipient at delivery time.
4. **Audit chain unbroken.** Every dispatched / queued / sent / failed /
   rejected step appends to the activities ledger or audit_events with a
   correlation_id pointing back at the originating activity.

---

## 1. Two-table schema

### 1.1 `federation_inbox`

One row per inbound activity from a peer. Closed-set `status` per the
§12.1 reject reason catalogue:

```sql
CREATE TABLE federation_inbox (
    id              UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    activity_uri    TEXT         NOT NULL UNIQUE,  -- §1.invariant 2 dedup key
    peer_id         UUID         NOT NULL REFERENCES federation_peers(id) ON DELETE CASCADE,
    actor_uri       TEXT         NOT NULL,
    activity_type   TEXT         NOT NULL,
    object_kind     TEXT         NULL,
    object_id       UUID         NULL,
    envelope_json   JSONB        NOT NULL,            -- the verified envelope as received
    http_sig_key    TEXT         NOT NULL,             -- key URL used to verify HTTP-Sig
    received_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    status          TEXT         NOT NULL DEFAULT 'pending'
        CHECK (status IN ('pending', 'processed', 'rejected', 'failed')),
    reject_reason   TEXT         NULL,                 -- §12.1 catalogue when rejected
    dispatch_attempts INT        NOT NULL DEFAULT 0,
    last_attempt_at TIMESTAMPTZ  NULL,
    last_error      TEXT         NOT NULL DEFAULT '',
    processed_at    TIMESTAMPTZ  NULL,
    correlation_activity_id UUID NULL REFERENCES activities(id) ON DELETE SET NULL
);

CREATE INDEX federation_inbox_pending_idx
    ON federation_inbox (received_at) WHERE status = 'pending';
CREATE INDEX federation_inbox_by_peer_idx
    ON federation_inbox (peer_id, received_at DESC);
CREATE INDEX federation_inbox_by_status_idx
    ON federation_inbox (status, received_at DESC);
```

### 1.2 `federation_outbox`

One row per (activity × destination peer). A single aa:Share to a peer
with two specific recipients produces TWO outbox rows (one per
recipient, each with its own NaCl-box envelope when encryption applies).

```sql
CREATE TABLE federation_outbox (
    id                  UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    activity_id         UUID         NOT NULL REFERENCES activities(id) ON DELETE CASCADE,
    peer_id             UUID         NOT NULL REFERENCES federation_peers(id) ON DELETE CASCADE,
    target_user_url     TEXT         NULL,            -- NULL = broadcast within peer
    status              TEXT         NOT NULL DEFAULT 'queued'
        CHECK (status IN ('queued', 'sent', 'failed', 'cancelled')),
    attempts            INT          NOT NULL DEFAULT 0,
    next_attempt_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    last_attempt_at     TIMESTAMPTZ  NULL,
    last_response_code  INT          NULL,
    last_error          TEXT         NOT NULL DEFAULT '',
    sent_at             TIMESTAMPTZ  NULL,
    cancelled_reason    TEXT         NOT NULL DEFAULT '',
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

CREATE INDEX federation_outbox_ready_idx
    ON federation_outbox (next_attempt_at)
    WHERE status = 'queued';
CREATE INDEX federation_outbox_by_activity_idx
    ON federation_outbox (activity_id);
CREATE INDEX federation_outbox_by_peer_idx
    ON federation_outbox (peer_id, status, next_attempt_at);
```

### 1.3 Why two tables (not one)

Inbox + outbox have asymmetric shapes:
- Inbox stores the entire envelope as JSONB (we receive it verbatim).
- Outbox stores per-recipient delivery state but the envelope is re-built
  per attempt (recipient keys may rotate between attempts).
- Inbox dedups on `activity_uri` (sender's canonical URI); outbox doesn't
  need that — `(activity_id, peer_id, target_user_url)` is its uniqueness.

Combined-table designs collapse this asymmetry awkwardly. Two tables read
cleanly + index cleanly per the per-purpose hot path.

## 2. Inbox

### 2.1 HTTP endpoint

`POST /federation/inbox` — no cookie / bearer auth; auth is via
HTTP-Signature on the request itself.

Request shape:
- Body: JSON envelope per `docs/spec/federation/v1.md` §3.
- Headers: `Date`, `Digest: SHA-256=<base64-sha256(body)>`,
  `Signature: keyId="...",algorithm="hs2019",created=...,
  headers="(request-target) host date digest",signature="..."`
  per §10.

### 2.2 Pipeline (each stage drops the activity + records to inbox row on failure)

| # | Stage | Failure → status / reason |
|---|---|---|
| 1 | Parse request body as JSON envelope | `400` + no inbox row (malformed) |
| 2 | Check `@context` | `rejected` / `invalid_context` |
| 3 | Resolve actor → peer via `federation_peers` | `rejected` / `unknown_peer` |
| 4 | Confirm peer is `enabled` + `status='connected'` | `rejected` / `peer_disabled` |
| 5 | Verify HTTP-Signature using peer's `instance_public_key` | `rejected` / `sig_invalid` |
| 6 | Check `Date` is within ±5min | `rejected` / `stale_request` |
| 7 | Dedup on `activity_uri` (UNIQUE INDEX) | `200 OK` + no-op (already received) |
| 8 | Verify envelope signature (the per-actor Ed25519) | `rejected` / `sig_invalid` |
| 9 | Decrypt NaCl-box payload if `encryption` present | `rejected` / `plaintext_type_mismatch` |
| 10 | INSERT `federation_inbox` row with `status='pending'` | `500` (DB error) |
| 11 | Return `202 Accepted` to peer immediately | — |
| 12 | Background worker picks up + runs `CanPeerAccess` gate | `rejected` / `unshared_object` (audit emitted via `Recorder.ActivityRejected`) |
| 13 | If allowed: dispatch to domain handler (depends on activity type) | `failed` (with retry) or `processed` |

Stages 1-11 happen synchronously in the HTTP handler — the peer needs a
prompt 202. Stages 12-13 happen in a background goroutine. Decoupling
keeps the HTTP path predictable + lets us retry domain-side handler
failures without re-fetching from the peer.

### 2.3 Why HTTP returns 202 BEFORE dispatch

The HTTP signature + envelope signature already proved provenance +
integrity. The gate + domain dispatch is internal logic; a failure there
shouldn't bubble back to the peer (which can't act on the failure
anyway). 202 says "I have it durably; I'll handle it." A subsequent
retry from the peer dedups via `activity_uri` UNIQUE.

### 2.4 Dispatch handlers (per activity type)

The worker maps `federation.ActivityType` → handler function. Per the
1.22.C `ActivityRequiredScope` table:

| Type | Handler responsibility |
|---|---|
| `Like` | social.HandleInboundLike — insert a like row scoped to the sender |
| `Create` (Note) | social.HandleInboundComment |
| `Create` (Post) | posts.HandleInboundPost (mirror-receive) |
| `aa:Annotation` | annotations.HandleInbound (when annotations ship) |
| `aa:Share` | shares.HandleInboundShare — record "this peer shared X with me" |
| `aa:Unshare` | shares.HandleInboundUnshare — purge cached bytes |
| `aa:RevokeShare` | normalize → aa:Unshare per the locked-in §12.5 #3 |
| `Follow` | social.HandleInboundFollow → creates pending follow request |
| `Accept(Follow)` | social.HandleInboundAcceptFollow → upgrades to follower share row |
| `Undo(Follow)` | social.HandleInboundUndoFollow → revokes the follower share |
| `Delete` | dispatch to the relevant domain based on the object kind |
| `Update` | same |
| (unknown) | `failed` + audit; retry once then dead-letter |

Most handlers are not yet implemented (1.22.D is the first time we have
real inbound payloads to dispatch). This proposal includes ONLY the
wiring + a no-op handler for each verb that logs + records `processed`
without doing the domain write. **Real handlers ship per-domain in
follow-up phases.** That keeps 1.22.D scoped: the transport + the
dispatch map; not the domain re-receive logic.

### 2.5 Caching

- Peer lookup hot path uses `peer.Registry.ByURL` (already cached by
  1.22.B-bis).
- The HTTP signature key lookup uses `peer.instance_public_key` from the
  same cache.
- No per-inbox-row caching — each row is processed once + reads its own
  bytes from the DB.

## 3. Outbox

### 3.1 When rows get inserted

Per ADR 0044 the activities table is the source of truth. The outbox is
a projection of "this activity, for each peer that should receive it."

Three trigger points enqueue outbox rows:

1. **aa:Share grant** (1.22.C-c admin handler) — one outbox row per
   target_user_url (or one broadcast row if NULL).
2. **aa:Unshare revoke** (1.22.C-c + 1.22.C-d sweeper) — one outbox row
   per peer the share was with.
3. **Domain activity** (Like, Create(Note), Create(Post),
   aa:Annotation, etc.) — when the activity row commits, the dispatcher
   reads ALL active `federation_shares` rows for the activity's target
   object (via the §3.2 visibility resolver). One outbox row per
   resulting peer × target_user_url combo.

The dispatcher runs as part of `WithEmissionFn`'s post-commit hook (so
the outbox rows commit in the same transaction as the originating
activity). If the dispatcher fails (e.g. share-table read error), the
whole transaction rolls back — same write-ahead invariant as 1.22.C-c.

### 3.2 Visibility resolver (used by step 3 above)

Given an activity targeting `(object_kind, object_id)` published by user
U with visibility V:

- `private` / `org-only` — no federation; zero outbox rows.
- `followers` — query `federation_shares WHERE object_kind='user' AND
  object_id=U_UUID AND revoked_at IS NULL` for the follower-share rows;
  one outbox row per row.
- `explicit-share` — query `federation_shares WHERE object_kind=X AND
  object_id=ID AND revoked_at IS NULL`; one outbox row per row. PLUS
  containment: also covers activities on assets inside shared
  collections / workspaces (per the inbox-filter §5.1 logic, mirrored).
- `public` — reserved per the 1.22.C design; rejected at write.

### 3.3 Delivery worker

Background goroutine, ticker-driven (default 5s).

Per tick:
1. SELECT next N (default 100) `federation_outbox` rows
   WHERE `status='queued' AND next_attempt_at <= NOW()`
   ORDER BY `next_attempt_at`.
2. Group by peer (HTTP keep-alive friendliness).
3. For each row:
   - Re-fetch the activities row (envelope rebuild).
   - Fetch the recipient actor URL's pubkey if encryption applies.
   - Wrap with NaCl-box per §6.3 if needed.
   - Sign with our instance's per-actor private key.
   - Sign the HTTP request with our instance Ed25519 key per §10.
   - POST to peer's `/federation/inbox`.
   - On 2xx → status='sent', `sent_at=NOW()`.
   - On 4xx (non-retryable) → status='failed', record `last_error`.
   - On 5xx / timeout → increment `attempts`, set
     `next_attempt_at = NOW() + backoff(attempts)`; max 5 attempts then
     status='failed'.

### 3.4 Backoff policy

Exponential with cap:
- Attempt 1 → instant (queued at NOW())
- Attempt 2 → +30s
- Attempt 3 → +5min
- Attempt 4 → +1h
- Attempt 5 → +6h
- > 5 → `failed`

### 3.5 Cancellation

`status='cancelled'` is set by:
- Defederation cascade (peer's outbox rows cancelled in the chunked job).
- Admin manual cancel (admin UI button — 1.22.D-c).

### 3.6 Caching

- Peer URL lookup uses the per-peer cache (1.22.B-bis).
- HTTP client uses connection pooling (Go stdlib default).
- No outbox-row caching — each delivery is one-shot.

## 4. Audit events

Three new event types (already declared in 1.22.C-d but only used by
the gate-rejection path):

| Event | When fired | Payload |
|---|---|---|
| `federation.activity.received` | inbox row INSERTed with status=pending | activity_id, peer_id, actor_uri, activity_type, object_kind, object_id |
| `federation.activity.dispatched` | inbox row transitions pending→processed | activity_id, peer_id, target_handler |
| `federation.activity.rejected` | inbox row marked rejected (already exists) | activity_id, peer_id, reason, correlation_id |
| `federation.delivery.sent` | outbox row transitions queued→sent | activity_id, peer_id, target_user_url, attempts, response_code |
| `federation.delivery.failed` | outbox row exhausts retries → failed | activity_id, peer_id, target_user_url, attempts, last_error |
| `federation.delivery.cancelled` | outbox row cancelled | activity_id, peer_id, reason |

## 5. Sub-phase breakdown

| Sub-phase | Deliverable | Scope |
|---|---|---|
| **1.22.D-a** | Schema migration + inbox HTTP endpoint + sync pipeline (stages 1-11) + the dispatch goroutine framework (stage 12-13 with no-op handlers). Tests cover each §12.1 reject reason. | medium |
| **1.22.D-b** | Outbox table + the post-commit dispatcher (§3.1) + the delivery worker (§3.3) + backoff (§3.4). Hooks into existing aa:Share / aa:Unshare emission paths. Tests cover happy path + retry + dead-letter. | medium |
| **1.22.D-c** | Admin UI views (`/admin/federation/inbox` + `/admin/federation/outbox`), per-row retry/cancel buttons, defederation-cascade integration (cancels outbox rows). Audit-event types wired. | small |

Each sub-phase commits independently. -a + -b together make federation
actually work end-to-end (a sent aa:Share lands in the other peer's
inbox + records "shared with me"). -c is the operational layer.

## 5.5 Reviewer answers + additions (locked-in)

### Q1 — Dispatch handlers: Like + Comment land for real in 1.22.D-a

Stub every other verb. The wire-layer integration test is otherwise
weak (only proves a row landed in `federation_inbox`, not that
dispatch actually invoked domain code). Like + Comment are mechanical
ports of the existing local handlers scoped to a remote actor; ~100
LOC each + 2 integration tests. Two paired demo peers exchanging a
Like end-to-end is the minimum-viable "federation actually works"
demo and belongs in 1.22.D-a.

Defer Follow / Accept / Undo (state-machine complexity), aa:Share /
aa:Unshare (federation_shares maintenance from inbound),
aa:Annotation (annotation infra not landed), Update / Delete
(object-kind dispatch). Those land in per-domain follow-ups using
the 1.22.A-bis retrofit pattern.

Scope guardrail: if the Like+Comment handlers balloon past ~100 LOC
each, drop back to stubs-only for 1.22.D-a and ship the real
handlers in a focused follow-up.

### Q2 — Single worker with aggressive HTTP timeouts

Single inbound-dispatch worker + single outbound-delivery worker for
v1. Math: 100/tick × 5s ticks = 1,200 processings/min — ten times the
walled-garden scale we expect.

**Guardrail (required):** aggressive per-HTTP-request timeouts on the
outbox delivery client — `5s connect`, `10s total`. Hung peer becomes
a stream of 5xx-equivalent attempts that backoff naturally per §3.4
instead of blocking the whole queue.

**Refactor trigger** to a per-peer concurrency pool: "p95 outbox
dispatch latency exceeds 30s." Documented in the operational runbook
so the metric is the trigger, not vibes.

### Q3 — Backoff schedule approved

30s → 5min → 1h → 6h → fail after 5 attempts (~7 hours total). Right
window for a known-peers walled garden: covers maintenance windows
+ planned outages; fails fast enough that recipients see same-day.

**Tie-in to 1.22.D-c:** the admin UI MUST expose a "re-queue" button
on `status='failed'` rows. A peer recovering from a 24-hour outage
should let an operator re-trigger delivery without re-emitting the
activity (which would change `activity_uri` + lose the audit chain).

### Q4 — Defederation cascade uses direct fire-and-forget, NOT the outbox

The cascade job emits `aa:Unshare` as direct HTTP POSTs to the
peer's `/federation/inbox`, swallows any failures, then proceeds
with the peer DELETE. **Skip the outbox entirely for these.**

Reasoning:
- The outbox is for activities that should retry on failure. Cascade
  unshares are "do this once, ignore failures, move on." Semantics
  don't match.
- Keeps defederation atomic + bounded in time. Operator clicks
  "Defederate"; within seconds the peer is gone + we tried our best
  to notify them.
- Avoids the chicken-and-egg: queue Unshare → DELETE peer →
  FK CASCADE wipes the queue → Unshare never delivered.

Trade-off: the peer's local cached bytes survive without the
notification. Acceptable because access is already revoked on our
side — they can't act on those bytes beyond local viewing.

**Implementation:** the 1.22.C-d defederation cascade job gets a
narrow `notifyPeerOfUnshare(peer, share)` helper that builds the
envelope + signs the HTTP request + POSTs directly. Audit emission
happens locally regardless of HTTP outcome.

### Q5 — Hand-roll HTTP-Signatures

Locked. go-fed/httpsig is GPL-3 (contamination risk per ADR 0040 for
any future premium / cloud-bridge code). ory/x/httpx is Apache-2 but
a subset of what we need — worse footprint than owning the ~150
lines.

Spec already pins us to `hs2019` + `ed25519` only; the parser
surface is small. Conformance vectors land in
`testdata/conformance/http-sig/` alongside the envelope-signature
vectors per the 1.22.A pattern.

### Q6 — 2MB payload cap + 413

Approved. Envelopes carry metadata + signatures (few KB) + optional
NaCl-box payload (rarely >100KB) + embedded content (Note/Comment
text, Annotation strokes — usually <100KB). Asset bytes go through
CAS fetch endpoints; never inline in an envelope. 2MB is plenty.

Overflow returns `413 Payload Too Large` with a structured error
body (`{"error":"envelope too large; use CAS URIs for content","limit":"2MB"}`)
so the sending peer's operator gets actionable feedback.

### Addition A — Per-peer rate limit on /federation/inbox

A misbehaving peer (or compromised peer key) could spam the inbox
with millions of malformed-but-signed requests. Each request burns
CPU on signature verification before dedup fires. DoS surface.

**Required:** per-peer token-bucket rate limit. Default 100 req/sec
per peer; configurable via `sysconfig`. Exceeded → `429 Too Many
Requests` with `Retry-After` header.

**Placement in the pipeline:** AFTER HTTP-Signature verification (so
unauthenticated junk still gets rejected at sig_invalid) but BEFORE
envelope verification + DB write. Bounds CPU per peer at known cost.

**Implementation:** in-memory `peer_id → tokenBucket` map maintained
by the inbox handler. Cheap. Survives process restarts losing only
the bucket state (a peer could burst 100 + immediately restart-storm
us — bounded by 100 anyway).

### Addition B — Replay protection: envelope `id` UNIQUE is primary; Date is defense-in-depth

§2.2 stage 6 (`Date ±5min`) + §2.2 stage 7 (`activity_uri` UNIQUE)
together give replay protection. The race window — captured-then-
replayed within 5min, second arrival before first inbox row commits
— is closed by the DB UNIQUE constraint on `activity_uri` (which
maps to the envelope `id` field).

**Document in v1.md §10:** the envelope `id` UNIQUE constraint IS
the replay-protection primitive; the Date check is defensive
secondary. Future implementers must keep BOTH.

No schema change needed — the table already has `UNIQUE` on
`activity_uri`.

## 6. Open questions for the reviewer

1. **Inbox dispatch handler stubs.** This proposal ships no-op
   handlers for every activity type — they record `processed` in the
   inbox row but don't write to domain tables. Real handlers (e.g.
   "when I receive an inbound Like, INSERT a like row scoped to the
   sender peer") are per-domain follow-ups. **Confirm this scoping** —
   alternative is to land at least the trivial ones (Like, Comment) in
   1.22.D-a so the demo "two paired peers exchange a like" works
   end-to-end.

2. **Dispatch concurrency.** §2.4 worker is single-goroutine per
   instance. At 100/tick × 5s ticks = 1200 inbox processings/min.
   Adequate for the small-N peer count we expect early. **Confirm
   single-worker is OK** — alternative is per-peer concurrency caps
   (similar to the existing job queue pattern).

3. **Backoff schedule** (§3.4). 5 attempts over ~7 hours total. Confirm
   or override.

4. **Outbox row cancellation on defederation.** The peer DELETE cascade
   (FK ON DELETE CASCADE) already wipes outbox rows when the peer row
   goes. But the 1.22.C-d defederation-cascade JOB intentionally
   sequences: aa:Unshare first (which queues outbox rows), then DELETE
   peer (which wipes them). Net effect: aa:Unshare is queued but
   immediately cancelled. **Confirm desired behavior** — alternative
   is to flush the outbox FIRST then delete the peer (best-effort
   delivery of aa:Unshares before the peer's row disappears).

5. **HTTP-Signatures library.** Three options: hand-roll (small,
   no deps), use github.com/go-fed/httpsig (battle-tested, GPL-3
   licensed → must avoid), or use github.com/ory/x/httpx (Apache-2,
   smaller subset). **Recommend hand-rolling** — the spec already
   pins us to `hs2019` + `ed25519` only, and the parser is ~150 lines.
   Avoids a GPL dep + keeps the surface small.

6. **Inbox payload size cap.** Reasonable max for an envelope? 1MB
   covers any plausible Note / Comment / Share / Annotation; a Create
   wrapping a 4K-image-bytes-encrypted asset would be larger. Likely
   never inline (CAS URIs handle byte transfer separately). Suggest
   2MB cap with rejection on overflow.

Ready when you are.
