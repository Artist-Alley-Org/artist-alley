# Artist Alley federation protocol — v1

**Status:** shipped (1.22.D, 2026-06-08) — spec v1.0 (final, stamped 2026-07-13)
**ADR:** [0043 — Federation walled-garden protocol](../../adr/0043-federation-walled-garden-protocol.md)

**Approved sources:** [SOURCES.md](./SOURCES.md)
**Contributor register:** [CONTRIBUTORS.md](./CONTRIBUTORS.md)

This document is the **wire-format contract**. The Go implementation in
`app/internal/federation/` is one expression of this contract; a
re-implementer in any language must be able to interoperate using
only this document plus the conformance vectors at
`app/internal/federation/testdata/conformance/`.

When this document and the implementation drift, this document
wins, and the implementation is the bug.

This document is the **normative ArchivePub v1 contract**.
[`docs/protocol/archivepub.md`](../../protocol/archivepub.md) is a
non-normative overview and design rationale; where the two disagree,
this document governs.

### Implementation status (non-normative, updated 2026-11-17)

This section is **not** part of the contract. It records where the
reference implementation in `app/internal/federation/` currently
deviates from this document, so implementers are not misled. Items D2
to D8 below are open gaps: each is a defect in the implementation, not
a relaxation of the requirement, and stays open until fixed. The
*Resolved gap* paragraph after them (D1) records an implementation gap
that has since been closed, with what changed for peers. The
*Resolved discrepancy* paragraph (D9) records a past mismatch that came
from this document's own text, not from the implementation. Both are
kept for implementers who read the earlier wording. The *Specified, not

complete on paper but that the reference implementation neither emits

  fields inside `signature` and `encryption`, but keeps unknown

  receiver applies `Like` and comment `Create` only

  endpoint exist yet.
- **D6, per-activity definitions (§7.5).** The

- **D7, undocumented hint fields.** The receiver reads optional

- **D8, encryption key identifiers (§6.6).** The receiver does not use
  `sender_key_id`, `sender_key_version`, `recipient_key_id` or

**Resolved gap.**
**D1, per-actor envelope signatures (§5.3, §5.6, §6.4), resolved
2026-11-17 (#1526).** Until that date the sender did not sign envelopes
with the actor's key: `outbox` delivery emitted a placeholder `value`
(`activities.SetActivitySignature` had no caller), and the receiver
checked only that the `signature` block was present and that `type` was
`"Ed25519"`, so activities were authenticated per instance (§10), not
per actor. Now the outbox signs every envelope with the emitting
actor's Ed25519 key under the key id `<actor>#main-key`, after any
encryption so the signature covers the ciphertext (§6.4), and never
sends an envelope it cannot sign. Each instance serves an actor
document at the actor URI (§8.3). The inbox, single and batch, verifies
every envelope per §5.3 before storing anything: the actor must be a
`/users/<name>` actor of the peer whose instance signature authenticated
the request (otherwise `unknown_actor`, decided before any key lookup),
the key id must be `<actor>#main-key` (`unknown_key`), the value must
decode to 64 bytes (`sig_malformed`) and the signature must verify
(`sig_invalid`). A key that cannot be fetched right now is a retryable
`503`, never a reason to accept the envelope unverified. The key is
fetched once from the sending peer's actor document and pinned, trust on
first use; it is never replaced automatically. Key rotation is not
implemented (#1581): an actor whose key changes is refused with
`sig_invalid` until an operator clears the pin. **Compatibility:** a
peer still running an earlier release advertises the same
`ed25519-envelope-sig` capability but sends the placeholder. It stays
paired and needs no re-pair, but every envelope from it is refused with
`sig_malformed` until it upgrades.

**Resolved discrepancy.**
**D9, share scope catalogue (§7.5.1), resolved 2026-11-17 by erratum

**Specified, not yet implemented.**

## §1 Scope

The Artist Alley federation protocol is **ActivityPub-shaped** but
**artist-alley-to-artist-alley only at v1**. It is not Mastodon-
compatible. The parser rejects payloads carrying a non-artist-alley
`@context` value. The escape hatch to a future public-fediverse
translator is preserved by discipline (custom types map cleanly to
standard equivalents) but no translator ships at v1.

### §1.1 What this spec covers

- The on-the-wire envelope every activity uses (§3).
- The RFC 8785 canonicalization rules the envelope signature
  depends on (§4).
- The Ed25519 signature scheme (§5).
- The per-recipient NaCl-box `encryption` block (§6.5 policy, §6.6
  shape). *Erratum E2 (2026-10-21): this line previously named the
  multi-recipient envelope of §6.1 to §6.3, which is historical.*
- The activity + object vocabulary, including the custom `aa:*`
  types (§7).
- The actor-identity URI shape and the immutability constraint that
  preserves cross-instance references (§8).
- The conformance-vector test pack every implementation validates
  against (§9).
- Negotiated profiles, the one way to add envelope members within
  `protocol/v1` (§16), and the archival profile `archival-1`, which
  carries what a receiving archive needs to preserve an asset and
  prove its files arrived intact (§17).

### §1.2 What this spec does NOT cover (in v1)

- HTTP transport (inbox/outbox endpoints, delivery worker, retry
  policy). Spec'd separately in `v1-http.md` when Phase 1.22.D
  lands.
- Peer registry + handshake protocol. Phase 1.22.B.
- The `federation_shares` access-control layer. Phase 1.22.C.
- HTTP-Signatures algorithm details beyond the allowlist in §10.
  Full HTTP-Sig spec lands with 1.22.D.
- CAS fetch endpoint authorization. Phase 1.22.F.
- Key rotation. **Deferred to Phase 1.22.K.** v1 assumes one
  keypair per actor for life; rotation is operator-driven (re-issue
  identity, break federation references).
  *Erratum E5 (2026-10-21): this applies to actor signing keys only.
  Encryption (X25519) keys rotate with a retained-key grace window
  (ADR 0049, Decision 4; §6.6).*
- Auto-sync policies. **Deferred to Phase 1.22.J.** v1 default is
  manual `aa:Share` for every shared object.

## §2 Notation

- Field names are JSON object keys, case-sensitive.
- Required fields are marked **REQUIRED**; optional fields **OPTIONAL**.
- The keyword **MUST** is RFC 2119.
- "Peer" means an Artist Alley instance the local instance has
  paired with via the handshake in §11 (1.22.B). "Actor" means a
  single user account, identified by §8's URI shape.

## §3 Envelope

Every activity is a JSON object matching this shape:

```jsonc
{
  "@context": "https://artist-alley.org/protocol/v1",   // REQUIRED, exact string match
  "type":     "aa:Approve",                              // REQUIRED, see §7
  "id":       "https://studio-a.example/activities/UUID", // REQUIRED, see §8
  "actor":    "https://studio-a.example/users/alice",    // REQUIRED, see §8
  "published":"2026-06-04T10:00:00Z",                    // REQUIRED, RFC 3339
  "to":       ["https://studio-b.example/users/bob"],    // OPTIONAL, array of actor URIs
  "cc":       [],                                        // OPTIONAL, array of actor URIs
  "object":   "https://studio-a.example/assets/UUID",    // CONDITIONAL; type-dependent
  "aa:*":     "...",                                     // type-specific fields, see §7
  "encryption": { /* see §6.6 */ },                      // CONDITIONAL; replaces the type-specific fields (erratum E2a)
  "signature": {                                         // REQUIRED on every envelope (§5.6); covers any 'encryption' block (§6.4)
    "type":      "Ed25519",                              // REQUIRED, exact string match (v1)
    "publicKey": "https://studio-a.example/users/alice#main-key", // REQUIRED
    "value":     "base64url-no-padding-signature-bytes"  // REQUIRED, see §5
  }
}
```

> **Erratum E2a (2026-10-21).** Until this date the example above showed
> the historical `encrypted` field (§6.1) and a conditional signature.
> The deployed and normative field is `encryption` (§6.6), and the
> signature is required on every envelope (§5.6).

### §3.1 `@context` is a version string

`@context` MUST equal the exact string
`https://artist-alley.org/protocol/v1`. It is **not** a JSON-LD
context. The parser performs string equality, not LD context
resolution.

A payload with any other `@context` value MUST be rejected with
inbox status `invalid_context` (see §12).

The identifier is deliberately opaque. No JSON-LD context document
is published for it, and none is planned for v1.

### §3.2 Unknown fields are rejected, not ignored

Implementations MUST reject (not silently ignore) any top-level
field in an envelope, object, or `aa:*` extension that this
document does not define. Future additions to the vocabulary go
through versioning (`@context` → `protocol/v2`), not silent field
addition.

The one exception is a negotiated profile (§16): a member a profile
defines is not unknown between two peers that negotiated that profile,
and is unknown everywhere else. A profile does not relax this rule; it
names, in advance and frozen, the members it adds.

Rationale: silent unknown-field tolerance is the dominant cause of
fediverse interop bugs (each implementation invents its own
extensions, none can rely on the others honouring them). Rejecting
at the parser prevents Mastodon-style "Pleroma-only fields" drift
inside the walled garden.

> **Implementation status:** the reference implementation does not
> yet enforce this for top-level fields (D2) and reads two undefined
> hint fields (D7). See *Implementation status* above.

### §3.3 Field ordering is irrelevant on the wire

JSON object key ordering on the wire does not change semantics.
Implementations MUST canonicalize (§4) before signing or verifying;
the canonical form has a defined ordering and the signature is
computed over the canonical bytes.

### §3.4 Empty arrays vs. omitted fields

`to: []` and an omitted `to` field are semantically equivalent
("the activity has no specifically-named direct recipients"). The
canonicalization in §4 normalizes both to "field omitted" so
signatures match.
### §3.5 Performance contract (latency)

Federation activity propagation targets **sub-second end-to-end**
(local commit → remote inbox dispatched → recipient-visible side
effect) through LISTEN/NOTIFY on all three queue-shaped tables
in the pipeline:

- `activities` — local commits notify the outbox dispatcher.
- `federation_outbox` — enqueued rows notify the delivery worker.
- `federation_inbox` — landed rows notify the inbox dispatcher.

Tickers on each layer (default 30s) are **correctness backstop
only** for missed notifications under load (connection blip,
process restart mid-batch). They MUST NOT be relied on as the
primary signal; reducing them is acceptable for resource-
constrained deployments but raising the LISTEN cadence (e.g.
disabling triggers) is a wire-incompatible change to the
performance contract.

Targets:
- **p50:** sub-100ms (local commit → recipient-visible).
- **p99:** sub-1s in the happy path (paired peers, neither
  under load).
- **p99 under sustained load:** bounded by the slower side's
  recipient resolver + DB write throughput; the dispatch
  layer itself adds <50ms.

Implementations MUST emit the trigger functions described in
§10.3.5 (LISTEN channel names locked) so the contract holds
across implementations. A receiver that uses ticker-only
dispatch is conformant per the wire format but breaks the
latency contract — operators MUST be informed; admin UI
SHOULD surface this as a degraded-mode indicator.

The contract is validated end-to-end by
`TestFederation_EndToEnd_ProductionDefaults_SubSecond` in
the reference implementation — the test asserts sub-1s wall-
clock from local activity INSERT to remote `likes` row
materialisation using PRODUCTION tick intervals (no fixture
tuning). Regressions to the trigger layer or default tick
intervals will fail that test.

## §4 Canonicalization (RFC 8785)

The signed payload (the input to §5's Ed25519 signature) is the
**JSON Canonicalization Scheme** (RFC 8785) representation of the
envelope **with the `signature` field removed**.

### §4.1 Algorithm

The full algorithm is defined in
[RFC 8785](https://datatracker.ietf.org/doc/html/rfc8785). The
salient rules:

1. **Object keys are sorted lexicographically by UTF-16 code unit.**
   (Not UTF-8; not Unicode normalized — UTF-16. RFC 8785 §3.2.3.)
2. **Numbers serialize as their shortest IEEE 754 double-precision
   round-trip representation** (RFC 8785 §3.2.2). `1.0` becomes `1`,
   `1.500` becomes `1.5`, `-0.0` becomes `0`, NaN and ±Infinity are
   forbidden in JSON entirely so this is moot.
3. **String escaping is minimal.** Only the six required JSON
   escapes (`"`, `\`, `\b`, `\f`, `\n`, `\r`, `\t`) and `\uXXXX`
   for the ASCII control range C0. All other code points serialize
   literally as UTF-8.
4. **No whitespace.** No indentation, no trailing newline, no
   separators beyond what the JSON grammar requires.
5. **Arrays preserve their input order.** Only object keys reorder.

### §4.2 Why these rules matter

Two JSON serializers that both produce "valid JSON" can produce
**different bytes** for the same logical object. Without RFC 8785,
a re-encoded envelope (e.g. one logged and replayed) might not
verify against its signature. The canonicalization is what makes
signatures portable across implementations and across storage
round-trips.

### §4.3 Removal of the `signature` field before canonicalization

The `signature` field is **deleted** from the JSON object before
canonicalization. Implementations MUST NOT canonicalize a
representation containing the signature and then "subtract" the
signature bytes after — that path admits subtle equality bugs.
Delete-then-canonicalize is the single correct order.

Pseudocode:

```
canonical_bytes = JCS(delete_key(envelope, "signature"))
signature       = Ed25519_Sign(actor_private_key, canonical_bytes)
envelope["signature"] = { type, publicKey, value: base64url(signature) }
```

### §4.4 RFC 8785 baseline conformance vectors

The IETF appendix examples (RFC 8785 Appendix B) are reproduced
verbatim in `testdata/conformance/rfc8785/*.json` as the baseline
canonicalization conformance pack. A re-implementer MUST validate
their canonicalizer against the RFC 8785 vectors **before** any
artist-alley-specific signature work. These vectors are public-
domain per IETF Trust Legal Provisions.

Each vector is the pair `{input.json, canonical.bin}` where
`canonical.bin` is the byte-for-byte RFC 8785 output. An
implementation's canonicalizer is correct iff it produces exactly
`canonical.bin` for `input.json`.

## §5 Signature (Ed25519)

### §5.1 Algorithm

Pure Ed25519 per [RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032).
The signing key is the actor's per-user Ed25519 private key,
generated at user creation (Phase 1.22.A) and stored encrypted at
rest per §13. The public key is published at the actor URI's
`#main-key` fragment (the value of `signature.publicKey` in §3).

### §5.2 Encoding

The 64-byte signature is encoded as **base64url-no-padding** (RFC
4648 §5, no `=` padding) and placed in `signature.value`.

The public key is published in PEM format
(`-----BEGIN PUBLIC KEY-----`...) per RFC 8410 at the actor's
`#main-key` URL. PEM is the wire format for human-tooling
compatibility (`openssl pkey -text`, etc.); the bytes inside are
the 32-byte raw Ed25519 public key.

### §5.3 Verify procedure

Given a received envelope `E` and the sender's published public key
`PK`:

```
sig_b64  = E["signature"]["value"]
sig_bytes = base64url_decode_no_padding(sig_b64)
if length(sig_bytes) != 64: REJECT  (sig_malformed)

E' = delete_key(E, "signature")
msg = JCS(E')
ok = Ed25519_Verify(PK, msg, sig_bytes)
if not ok: REJECT  (sig_invalid)
```

The `publicKey` field in the envelope is a URL hint about where to
fetch the public key; the receiver MUST have already obtained `PK`
through the handshake (§11) and the actor's actor-doc fetch. The
envelope's `publicKey` URL is matched against the actor's known
keys; a mismatch is `unknown_key`.

### §5.4 Key fingerprint

For audit + debugging, a key fingerprint is the lowercase hex
SHA-256 of the 32 raw public-key bytes (NOT the PEM wrapper).

### §5.5 Algorithm allowlist

`signature.type` MUST equal the exact string `"Ed25519"`. No other
algorithm is accepted at v1. A future protocol version may add
algorithms but each will require a new `@context` version string.

### §5.6 Signature field requirement

The `signature` field is REQUIRED on every envelope. Implementations
MUST reject envelopes lacking the field — OR with the field present
but malformed (missing `type`, `publicKey`, or `value`) — with the
`envelope_sig_missing` reject reason per §12.1.

Per-actor signature verification is OPTIONAL at v1.0 (the 1.22.D
inbox phase) but MUST be implemented by v1.0 + 1 (the 1.22.I
encrypted-federation phase, which ships the per-actor public-key
distribution this verification depends on):

- A v1.0-only implementation accepts any well-formed signature
  block; structural validation only.
- A v1.0 + 1 implementation cryptographically verifies the
  signature against the per-actor public key resolved from
  `signature.publicKey`.

Implementations MUST NOT relax the structural requirement once
added. A future protocol version that drops the signature field
is a wire-incompatible break and requires a new `@context`
version string.

This split lets walled-garden federation operate in v1.0 (the
instance-level HTTP-Signature at §10 provides transport-integrity)
while ensuring the wire format is forward-compatible with the
end-to-end per-actor crypto verify that 1.22.I lands.

## §6 End-to-end encryption envelope (NaCl-box)

Activities targeting `restricted`- or `embargo`-tier objects (per
ADR 0020) optionally use a multi-recipient encryption envelope.
The plaintext fields are replaced with a single `encrypted` field;
the rest of the envelope (`@context`, `type`, `id`, `actor`,
`published`, `to`, `cc`, `signature`) remains in clear so the
inbox can authenticate the sender and dispatch the activity
without decrypting.

> **Erratum E2 (2026-10-21).** §6.1 to §6.3 describe the original
> multi-recipient `encrypted` block (ephemeral sender key, one
> envelope for many recipients). It was never produced, and receivers
> reject it with `encryption_not_supported`. The deployed and
> normative encryption envelope is the per-recipient `encryption`
> block of ADR 0049 (Track B, Decision 2), defined in §6.6. §6.1 to
> §6.3 are kept as historical, non-normative text; §6.2 (separate
> Ed25519 and X25519 keypairs per actor) and §6.4 (the signature
> covers the encrypted envelope) still apply.

### §6.1 Shape

```jsonc
{
  "@context": "https://artist-alley.org/protocol/v1",
  "type":     "aa:Annotation",
  "id":       "https://studio-a.example/activities/UUID",
  "actor":    "https://studio-a.example/users/alice",
  "published":"2026-06-04T10:00:00Z",
  "to":       ["https://studio-b.example/users/bob",
               "https://studio-c.example/users/carol"],
  "encrypted": {
    "alg": "nacl-box",                                    // REQUIRED, exact match
    "ephemeralKey": "base64url-32-bytes-X25519-pubkey",   // REQUIRED
    "recipients": [
      {
        "actor": "https://studio-b.example/users/bob",
        "nonce": "base64url-24-bytes",                    // REQUIRED, per-recipient
        "ciphertext": "base64url-encrypted-payload-for-bob"
      },
      {
        "actor": "https://studio-c.example/users/carol",
        "nonce": "base64url-24-bytes",
        "ciphertext": "base64url-encrypted-payload-for-carol"
      }
    ]
  },
  "signature": { /* §5; signs the encrypted envelope, not the plaintext */ }
}
```

### §6.2 Distinct X25519 keypair per actor

NaCl-box uses **X25519** for key agreement. Each actor holds
**two independent keypairs**:

- An **Ed25519** keypair used for envelope signatures (§5).
- An **X25519** keypair used for NaCl-box recipient encryption.

Both public keys are published in the actor doc; both private
keys are stored encrypted-at-rest (§13).

**Why two keypairs instead of deriving X25519 from Ed25519.**
The Edwards-to-Montgomery birational map (RFC 7748 §4.1) does
permit deriving an X25519 public key from an Ed25519 public key,
and several deployed federation protocols do this. Artist Alley
v1 explicitly does NOT, for two reasons:

1. **Key-separation hygiene.** Reusing one keypair across two
   cryptographic primitives concentrates compromise: an attack
   against the signature scheme contaminates the encryption
   scheme and vice versa. Signal, Matrix, and every modern
   secure-messaging design publish distinct keys per primitive.
2. **Implementation simplicity + audit surface.** The field
   arithmetic for the birational map is security-sensitive
   (constant-time inversion in GF(2^255-19)) and adds either a
   third-party dependency or ~200 lines of in-tree crypto code we
   then have to maintain. Generating two keypairs at user-create
   time is one extra `curve25519.GenerateKey` call and 32 more
   bytes per user in the DB.

The 32-bytes-per-user storage cost and the small operational
cost of distributing two keys instead of one are accepted for v1.

### §6.3 Per-recipient encryption

For each recipient `R`:

1. The sender generates a single ephemeral X25519 keypair `(ek, EK)`
   used across all recipients in this envelope (saves bytes).
2. For each `R`: compute the NaCl-box ciphertext using:
   - sender's ephemeral X25519 secret `ek`
   - recipient's **published** X25519 public key (§6.2 — distinct
     from their Ed25519 signing key)
   - a fresh random 24-byte nonce, unique per recipient
   - the plaintext (JCS-canonicalized JSON of the type-specific
     fields the plain envelope would carry — `object`, `aa:comment`,
     etc.)

The recipient's decrypt is the reverse: ephemeral pub key from
`encrypted.ephemeralKey`, sender-known recipient X25519 secret,
nonce from `recipients[i].nonce`, ciphertext from
`recipients[i].ciphertext`. The plaintext is JCS-encoded JSON
which the recipient parses into the type-specific fields.

### §6.4 Verifying the signature with encryption present

The envelope's `signature` (§5) covers the **encrypted** envelope,
not the plaintext. This means:

- Any peer that holds the sender's Ed25519 public key can verify
  the activity came from the sender, even if they're not on the
  recipient list (they cannot decrypt, but they can authenticate).
- A recipient who decrypts MUST additionally validate the
  plaintext shape matches the expected `type` once decoded; a
  mismatch (sender signed `aa:Annotation` but plaintext decodes as
  `aa:Approve`) is `plaintext_type_mismatch` and is logged.

### §6.5 When encryption is mandatory

> **Erratum E3 (2026-10-21).** The ADR 0043 list below is superseded
> by ADR 0049 (Track B, Decision 5) and is kept for history. The
> normative sender policy is the matrix that follows it.

Per ADR 0043 §"Encryption tier":

- `public` and `team`-tier objects: plaintext envelope.
- `restricted`-tier objects: encryption envelope REQUIRED when
  delivering over a peer link whose `federation_peers.encryption_policy`
  is `e2e-encrypted`.
- `embargo`-tier objects: encryption envelope REQUIRED **always**,
  regardless of peer policy.

A `restricted`- or `embargo`-tier activity sent without an
encryption envelope to a peer whose policy demands one is
`encryption_required` and MUST be rejected by the recipient.

**Normative sender policy (ADR 0049).** Per recipient peer, "can
encrypt" means the peer negotiated the NaCl-box capability AND the
recipient actor's X25519 public key is available:

| Object sensitivity tier | Can encrypt | Sender MUST |
|---|---|---|
| `public`, `team` | yes | encrypt (§6.6) |
| `public`, `team` | no | send plaintext |
| `restricted`, `embargo` | yes | encrypt (§6.6) |
| `restricted`, `embargo` | no | refuse: send nothing to that recipient, and record the refusal |
| unknown or future tier | yes | encrypt (§6.6) |
| unknown or future tier | no | refuse |

Refusal is per recipient: other recipients of the same activity are
unaffected. A receiver MUST reject a plaintext envelope whose target
object's tier requires encryption with `encryption_required`. The
same matrix appears, non-normatively, in `docs/protocol/archivepub.md`
§3.6; a change to one MUST be made to both in the same revision.

### §6.6 Per-recipient `encryption` block (normative)

Each encrypted envelope has exactly one recipient. The activity's
type-specific fields (everything outside `@context`, `type`, `id`,
`actor`, `published`, `to`, `cc`, `object`, `signature`) are removed
from the envelope, serialised as one JSON object, and sealed with
NaCl-box (X25519, XSalsa20, Poly1305) from the sender's current
X25519 key to the recipient's. The result is carried as:

```jsonc
"encryption": {
  "algorithm": "nacl-box-v1",                                    // REQUIRED, exact match
  "sender_key_id": "https://studio-a.example/users/alice#encryption-key",
  "sender_key_version": 3,                                       // integer >= 1
  "recipient_key_id": "https://studio-b.example/users/bob#encryption-key",
  "recipient_key_version": 1,                                    // integer >= 1
  "nonce": "base64-24-bytes",                                    // standard base64, fresh per emission
  "ciphertext": "base64"                                         // standard base64
}
```

- The sender uses its permanent X25519 keypair, not an ephemeral one.
- The nonce MUST be fresh random bytes for every emission.
- Unknown fields inside `encryption` MUST be rejected.
- The sender's key is resolved from the sender actor's published keys
  (ADR 0049, Decision 2); `sender_key_id` and `sender_key_version` name
  the key used to seal. `recipient_key_id` and `recipient_key_version`
  name the recipient key it was sealed to.
- The receiver MUST be able to decrypt with its current key or any key
  it retains within the rotation grace window (ADR 0049, Decision 4),
  and MUST reject with `decrypt_failed` when no key works. The version
  fields identify keys; this document does not require a receiver to
  select keys by them. The reference implementation does not use them
  to select keys (D8).
- The envelope `signature` (§5) covers the envelope including this
  block (§6.4).

#### §7.5.1 `aa:Share`

> **Erratum E7 (2026-11-17, #1524).** Until this date the `scope` line
> below read `view | comment | annotate | edit`. The fourth value was
> settled as `remix` in the 1.22.C share design review, before any
> code shipped, with `edit` reserved for a different future operation
> (`docs/proposals/1.22.C-shares-design.md`, "Scope ladder"). The
> reference implementation has used `remix` in its catalogue, database
> and API from the start, and has never accepted or emitted `edit`;
> only this document kept the earlier word. This erratum corrects the
> value set to the one every deployed instance uses and defines both
> words below. It adds no field and changes no `@context`: the identifier
> `https://artist-alley.org/protocol/v1` names this corrected contract
> and negotiates nothing, in the same way erratum E2a corrected a field
> name. The ADR 0043 amendment of the same date records the decision.

```jsonc
{
  "type":   "aa:Share",
  "object_kind": "post",                                   // REQUIRED: post | collection | workspace | brand_kit | asset | user
  "object": "https://studio-a.example/posts/UUID",         // REQUIRED
  "target_peer": "https://studio-b.example",               // REQUIRED, peer instance URL
  "target_user": "https://studio-b.example/users/bob",     // OPTIONAL, NULL = any user on that peer
  "scope":  "view",                                        // REQUIRED: view | comment | annotate | remix (erratum E7)
  "expires_at": "2026-12-31T23:59:59Z",                    // OPTIONAL
  /* envelope fields per §3 */
}
```

**Scope ladder (normative).** `view` < `comment` < `annotate` < `remix`.
Each scope includes everything the scopes below it allow.

| Scope | Allows the recipient to |
|---|---|
| `view` | read the object and react to it (`Like`, `Announce`) |
| `comment` | `view`, plus comment on it (`Create` of a comment) |
| `annotate` | `comment`, plus annotate it (`aa:Annotation`) |
| `remix` | `annotate`, plus reuse the shared material in the recipient's own objects on the recipient's own instance (posts, collections, workspaces, brand kits), referencing the shared bytes (§8.5) |

**Editing the original is not a v1 scope.** No scope above authorises
an activity that modifies the shared object on the instance that holds
it (the origin): its content, its metadata, its workflow state, or, for
a collection, its membership. `remix` creates new objects on the
recipient's instance and never changes the original. Changes to the
original are made by local users of the origin instance. The value
`edit` is reserved for a possible future scope that would allow editing
the original from another instance; it is not part of v1:

- A sender MUST NOT emit `"scope": "edit"`.
- A receiver MUST refuse an `aa:Share` whose `scope` is `edit`, or any
  value not in the ladder, without storing it, and MUST NOT treat `edit`
  as `remix` or as any other scope.
- A receiver MUST NOT admit an activity that would modify the original
  (for example an `Update` or `Delete` of the original, an
  `aa:WorkflowTransition`, or an `Add` / `Remove` on the original
  collection) on the strength of any share, whatever its scope.

**Compatibility with the earlier text.** An implementation written
against the text before erratum E7 that sends or expects `edit` does
not interoperate with the reference implementation on this field, and
never has: the reference refuses `edit` and sends `remix`, which the
earlier text did not list. Such an implementation should send `remix`
where its `edit` meant reusing shared material on its own instance, and
has no v1 equivalent where its `edit` meant changing the original. On
receipt, `remix` has the meaning above. The `@context` value does not
tell a peer which text another implementation followed; only the values
it sends do. No independent implementation is known (*Conformance
evidence scope*, above).

> **Clarification (2026-11-17, #1524).** `aa:Approve`,
> `aa:RequestChanges` and `aa:MarkReviewed` each record a reviewer's
> verdict about the object. None of them changes the object or its
> workflow state, and a receiver MUST NOT change either on receiving
> one. Moving an object to another workflow state is
> `aa:WorkflowTransition`, a separate activity that changes the

### §7.6 Activity types a receiver does not apply

> **Addition A1 (2026-11-16, #1569).** Until this date the contract
> said nothing about a §7 type the receiver has no handler for.

A receiver is not required to apply every §7 type, but it MUST NOT
acknowledge one it does not apply as received for processing. For an
envelope that has passed the §10 HTTP Signature, the §3.1 `@context`
check and the §5.6 signature-block check, a receiver that does not
apply the envelope's `type`:

- MUST answer it as rejected with reason `unsupported_activity`
  (§12.1): `422` on `POST /federation/inbox`, and a `rejected` result
  in a §10.4 batch;
- MUST give every later delivery of the same activity `id` the same
  answer, never the `200` / `replayed` idempotent receipt of §10.3.
  This holds after a restart and after the receiver starts applying
  that type: the stored refusal decides the answer, and the
  activity is not applied;
- MUST NOT later apply, or retry applying, an activity it refused
  this way, and SHOULD keep the envelope for operator diagnosis.

A receiver that cannot record the refusal answers a retryable
failure (`5xx`; `503` for a batch, §10.4), not
`unsupported_activity`: the refusal is final only once it is
stored.

A `type` outside §7 is not covered here: it fails parsing with
`invalid_type` (§3.2). A sender treats `unsupported_activity` like
any other §12.1 reason: the delivery is final and is not retried.
v1 has no handshake capability for activity types, so this rejection
is how a sender learns that a peer does not apply a type.

The reference implementation applies `Like` and comment `Create`
(*Implementation status* D3).

## §8 URI shape

### §8.1 Activity URIs

`https://{instance}/activities/{uuid}`

`{uuid}` MUST be UUID v4 in lowercase hex with hyphens (8-4-4-4-12).
The URI is the activity's `id` field.

### §8.2 Object URIs

`https://{instance}/{kind}/{uuid}`

`{kind}` MUST be one of: `posts`, `assets`, `collections`,
`workspaces`, `brand_kits`. Other kinds are reserved.

### §8.3 Actor URIs

`https://{instance}/users/{username}`

`{username}` is the user's stable handle. The actor URI is the
cross-instance identity for this user.

> **Clarification (2026-11-17, #1526): the actor document.** The actor
> URI serves the actor document a receiver obtains the actor's public
> key from (§5.3): a JSON object with `id` (the actor URI), `type`
> (`"Person"`), `preferredUsername`, and `publicKey`, whose `id` is the
> actor URI plus `#main-key`, whose `owner` is the actor URI and whose
> `publicKeyPem` is the RFC 8410 PEM of §5.2. The reference
> implementation serves it only to a `GET` carrying a valid instance
> HTTP Signature (§10) of an enabled, connected peer, so it is not an
> anonymous directory of users or keys; it answers `404` for an unknown
> user or one without a key and never redirects. As a receiver it
> fetches the document only for an actor URI on the authenticated
> sending peer's own origin, with its own instance-signed `GET`,
> follows no redirect, bounds the time and size of the response, and
> requires `id`, `publicKey.id` and `publicKey.owner` to match the
> actor URI exactly.

### §8.4 Username immutability

**Once a user account exists, the actor URI is the stable handle
for all cross-instance references.** Changing a user's username
breaks every federated reference to them (other peers' follow
graphs, share rows, audit-log actor pointers, prior activity
inboxes' actor_url fields).

The username-change admin surface (Phase 1.17.B-bis) MUST display
this consequence prominently. Once changed:

- Remote peers' inbound activities citing the old username 404.
- Remote followers' Follow rows no longer point at a live actor.
  The local user appears defederated to them until they re-follow.
- Local audit log entries naming the old username remain valid
  (the audit log is local truth).

This constraint matches Mastodon's policy and keeps the future
public-fediverse escape hatch intact. The alternative (UUID-keyed
actor URLs with username as a separate webfinger lookup) was
considered and rejected as more flexibility than v1 needs.

Display names are a SEPARATE field on the user profile and can
change freely without federation impact.

### §8.5 CAS URIs for asset bytes

> **Implementation status:** not implemented yet in the reference
> implementation (D5).

`cas://<sha256>?content-type=<mime>&size=<bytes>`

`<sha256>` is lowercase hex of the SHA-256 of the asset bytes per
ADR 0008. Query parameters are advisory metadata; the SHA-256 is
the only authoritative identifier.

CAS URIs appear in `aa:Asset` and `aa:AssetVersion` activities as
the content reference. Resolution rule (per ADR 0043 §"CAS-native
federation"):

1. Check local storage; if present, use directly (no transfer).
2. Else issue a signed GET to
   `{origin_instance}/assets/{sha256}/bytes` (Phase 1.22.F endpoint).
3. Cache the bytes locally; future references dedup against the
   cache.

The CAS-fetch endpoint guards on `federation_shares` per fetch —
a peer requesting bytes for a hash they don't currently hold a
share for receives 403.

`testdata/conformance/archival-1/`

## §10 HTTP transport (forward reference)

Full HTTP-Signatures spec lands with Phase 1.22.D. This section
locks two decisions now to prevent algorithm-confusion attacks
later:

### §10.1 Algorithm allowlist

Transport-layer HTTP-Signatures (the request-line signature on inbox
POSTs) accepts ONLY:

- `hs2019` with the `ed25519` key algorithm parameter

**Explicitly rejected:**

- RSA-PKCS1-v1_5, RSA-PSS, any RSA variant
- HMAC-SHA256 or any HMAC variant
- `rsa-sha256` (the legacy non-`hs2019` name)
- Any unspecified or future algorithm not in the allowlist above

Rationale: the historical fediverse HTTP-Sig deployment is RSA-
heavy; permitting RSA at our inbox creates a downgrade path. Locking
Ed25519-only matches our envelope signature scheme and keeps the key
material symmetric across both layers.

### §10.2 Signed headers (preliminary)

The inbox POST signature MUST cover at minimum:
`(request-target)`, `host`, `date`, `digest`. The `digest` header
is the SHA-256 digest of the request body, base64-encoded, prefixed
`SHA-256=`.

Replay window: 5 minutes. Requests with `date` skew beyond ±5
minutes from the receiver's clock are rejected (`stale_request`).

### §10.3 Replay-protection layering

Two complementary checks defend against replay:

1. **Envelope `id` UNIQUE at the inbox** — the load-bearing
   primitive. Every successfully-received envelope's `id`
   field MUST be persisted under a UNIQUE constraint
   (`federation_inbox.activity_uri`). A replayed envelope
   surfaces as a constraint-violation on insert → the
   receiver returns `200 OK` (no-op, already received). This
   is the authoritative dedup. An `id` that was refused as
   `unsupported_activity` is answered with that same rejection
   instead (§7.6). The receipt is only ever given for an `id`
   that is stored: a faster in-memory replay check that finds an
   `id` with no stored record MUST process the envelope as a
   first delivery, not acknowledge it.

2. **`Date` header window (±5min)** — defense-in-depth that
   front-loads the rejection. A replayed envelope from outside
   the window never reaches the DB insert; it fails with
   `stale_request` after HTTP-Sig verify.

Both MUST be implemented. Implementations MUST NOT relax
either as an optimisation; the combination protects against
"capture, hold for >5min, replay" (caught by UNIQUE) AND
"capture, replay immediately" (caught faster by Date but
also caught by UNIQUE). Removing the Date check would push
all replays to the DB insert; removing the UNIQUE would
permit replays of any envelope retransmitted within the
5min window before the first arrival's row commits.

### §10.4 Batched inbox

`POST /federation/inbox/batch` accepts an array of envelopes
in one request, amortising HTTP-Sig + TLS overhead across
all of them. The body MUST be a JSON object of shape:

```json
{
  "envelopes": [ {...envelope...}, {...envelope...} ]
}
```

Per-envelope constraints unchanged from §10.1-§10.3. Batch
constraints:

- MAX 50 envelopes per batch.
- MAX 1MB total body size (the singleton `/federation/inbox`
  cap from §3.10 of the 1.22.D design proposal applies to the
  batched body as a whole, NOT per-envelope).
- HTTP-Sig signs the WHOLE batched body (not each envelope
  individually); the receiver's HTTP-Sig verify covers transport
  integrity for all envelopes in one pass.
- Envelopes within a batch are processed IN ORDER. A failure
  on envelope N does NOT abort processing of envelope N+1.

Response (always 200 OK regardless of per-envelope outcomes —
the HTTP layer succeeded; individual envelope outcomes are
in the body):

```json
{
  "results": [
    { "activity_uri": "...", "status": "accepted",  "reason": "" },
    { "activity_uri": "...", "status": "replayed",  "reason": "" },
    { "activity_uri": "...", "status": "rejected",  "reason": "envelope_sig_missing" }
  ]
}
```

`status` is one of:
- `accepted` — landed in the inbox (will dispatch).
- `replayed` — already-seen activity_uri; idempotent no-op.
- `rejected` — typed reason from §12.1. This includes
  `unsupported_activity` for a type the receiver does not apply,
  on first delivery and on every duplicate (§7.6).

The receiver returns:
- **400** if the batched body itself is malformed (not the
  array shape, missing `envelopes` field, etc).
- **413** if total body exceeds 1MB.
- **401** if HTTP-Sig verification fails for the batched body.
- **503** if it cannot store an envelope, or cannot read the
  stored record of a duplicate. Every result in a `200` body is
  final for the sender, so an envelope the receiver failed to
  store MUST NOT be reported as `rejected` (or `accepted`); the
  sender retries the whole batch, and envelopes already stored
  are answered from their stored records on the retry
  (`replayed`, or the same rejection). *Added 2026-11-16 (#1569).*
- **200** with per-envelope `results` array in every other
  case.

Implementations MAY accept singleton POSTs to either endpoint
(`/federation/inbox` or `/federation/inbox/batch`); the batch
endpoint is the optimisation surface, not a replacement.

## §11 Peer handshake (forward reference)

Phase 1.22.B. The handshake establishes the two-way trust channel
described in ADR 0043 §"Trust model" — pairing creates the channel,
nothing else. Specified separately when 1.22.B lands.

For 1.22.A, the relevant constraint is: a peer's Ed25519
public key is established during handshake and stored in
`federation_peers.instance_public_key`. This key authenticates the
peer instance, distinct from the per-actor keys that sign envelopes.
Two layers of authentication, two distinct key spaces.

> **Note (2026-11-17, #1526).** The handshake does not exchange
> per-actor keys. A receiver obtains them from the actor document
> (§8.3), fetched over the channel the handshake authenticated (an
> instance-signed `GET` to the paired origin). Pairings made before
> #1526 need no re-pair.

> **Profiles (2026-11-17, #1513).** The `supported_capabilities` list
> also carries profile tokens (§16). Each side stores the intersection
> of the two lists at pairing, and that stored intersection is the only
> record of which profiles are in effect for the pair.

## §12 Status codes

Inbox + outbox dispatch results use a typed catalogue per ADR 0042.
Full enumerations live in `app/internal/federation/vocab.go`. The
ones referenced in this document:

### §12.1 Inbox rejection reasons

- `invalid_context` — `@context` field does not equal the
  protocol-v1 string.
- `unsigned` — HTTP-Sig layer: request missing required
  `Signature` header per §10.
- `envelope_sig_missing` — envelope layer: `signature` field
  absent OR present-but-malformed (missing `type`, `publicKey`,
  or `value`). Distinct from `sig_invalid` which means "field
  present and well-formed but cryptographic verify failed."
  These are different failure modes — separate reasons let
  operators distinguish "your peer is shipping spec-noncompliant
  payloads" from "your peer's key is compromised or drifted."
- `unsupported_algorithm` — `signature.type` not in the allowlist.
- `sig_malformed` — signature bytes wrong length or not decodable.
- `sig_invalid` — signature does not verify against the named key.
- `unknown_key` — `signature.publicKey` URL does not match any
  known key for the named actor.
- `unknown_field` — top-level field not in the spec.
- `unknown_actor` — `actor` URI does not resolve to a known actor.
- `unknown_peer` — sender's instance is not in `federation_peers`.
- `peer_disabled` — peer is in `federation_peers` but disabled.
- `unknown_object` — activity references an object that does
  not resolve to a local row on this instance. Either the host
  portion of the URL does not match our base URL (sender's
  outbox built a foreign URL) OR the UUID portion does not
  match any known object on this instance (object was deleted
  on our side, or never existed). Distinct from
  `unshared_object`: that one means "I have the row but you
  don't hold a share grant"; this one means "I don't have the
  row at all." The two have different remediation paths —
  `unknown_object` repeated points at the SENDER's outbox
  misconstructing URLs or holding stale references to deleted
  objects; `unshared_object` repeated points at the SENDER's
  local share-cache being out of sync with this instance's
  canonical share state.
- `unshared_object` — activity targets a known local object
  but the sender does not hold a current `federation_shares`
  row for it. Pure access-control rejection — the load-bearing
  security property in 1.22.C protects against this.
- `encryption_required` — plaintext envelope received for an
  object whose peer policy demands encryption. **Inverse of
  `encryption_not_supported`**: this one fires when the SENDER
  violated a MUST-encrypt rule (per ADR 0020 sensitivity tier
  + the receiver's peer-policy expectation).
- `encryption_not_supported` — encrypted envelope received but
  the RECEIVER hasn't shipped the X25519 keypair-per-user
  decode path yet (Phase 1.22.I). **Inverse of
  `encryption_required`**: this is a receiver-side capability
  gap, not a sender-side violation. Until 1.22.I lands, the
  receiver emits this reason for any inbound envelope whose
  top-level `encryption` field is present. Implementations
  MUST NOT conflate these two reasons; they signal
  fundamentally different failure modes and operator
  remediation paths.
- `plaintext_type_mismatch` — encrypted envelope decoded to a
  different `type` than the outer envelope declared.
- `unsupported_activity` — the envelope is authenticated and
  well-formed, and its `type` is in §7, but this receiver does not
  apply that type (§7.6). Final: the activity was not applied and
  will not be. Distinct from `invalid_type`, which means the type is
  not in §7 at all. *Added 2026-11-16 (#1569, Addition A1).*
- `profile_not_negotiated`: the envelope carries a member or type
  that a profile defines (§16), and the sending peer's stored,
  negotiated capabilities lack that profile. *Added 2026-11-17
  (#1513).*
- `archival_invalid`: an archival-1 member does not match §17
  (shape, bounds, placement or a field rule). *Added 2026-11-17
  (#1513).*
- `fixity_mismatch`: received bytes do not have the listed size or a
  listed checksum (§17.6). *Added 2026-11-17 (#1513).*
- `stale_request` — HTTP-Sig date skew beyond replay window.
- `replay` — activity `id` already present in `federation_inbox`.

### §12.2 Outbox dispatch statuses

- `queued` — enqueued for delivery, not yet attempted.
- `sent` — delivered successfully.
- `failed` — delivery exhausted retries; will not be reattempted
  without manual intervention.
- `cancelled` — operator cancelled delivery (e.g. defederation
  before flush).

### §12.3 Emission-skipped audit reasons

Some activities never enter the outbox at all — the sender-side
dispatcher refuses emission upfront. These produce a
`federation.emission.skipped` audit event with one of:

- `encryption_required_but_not_supported` — target object's
  sensitivity tier requires encrypted delivery (restricted /
  embargo per ADR 0020) but the sending instance hasn't shipped
  X25519 keypair-per-user yet (Phase 1.22.I). Inverse pair with
  the inbox-side `encryption_not_supported` reject reason from
  §12.1 — same root cause, different end of the wire. Activities
  skipped for this reason do **not** retroactively dispatch when
  1.22.I lands; operators re-emit by re-applying the share if
  they want backfill. The admin federation/shares page banner
  (1.22.D-a-6) surfaces the general gap; individual
  emission-skipped events stream into the admin log for
  per-activity queryability.
- `recipient_set_empty` — visibility resolver returned zero
  peers (no active federation_shares grants matched the
  activity's target object). Normal for local-only objects, and
  for a `public` object nobody has shared: public is local read
  visibility, and a public object reaches only peers holding a
  live explicit share of it, never every paired peer. Audit-logged
  so operators can confirm a "why didn't this federate?"
  investigation.
- `defederation_in_progress` — peer is in the middle of a
  defederation cascade per ADR 0043 §1.22.C-e; outbox rows
  to that peer are suppressed until the cascade completes.

## §13 At-rest encryption of actor private keys

Per-user Ed25519 private keys MUST NOT be stored in plaintext at
rest. The user table stores `private_key_pem_encrypted` (BYTEA);
the bytes are AES-256-GCM ciphertext with the host master key.

### §13.1 Master key

The host master key is a 32-byte random key sourced from the
`AA_MASTER_KEY` environment variable (base64-encoded). It is
**not stored in the database**. It is operator-managed (mounted
secret, KMS, sealed-secret, whatever the deployment uses).

If `AA_MASTER_KEY` is missing or malformed at boot, the federation
package fails to initialize and any operation requiring an actor
private key returns an error. The rest of the application
proceeds; federation is the only feature gated on the master key
at v1.

### §13.2 Ciphertext format

```
| version_byte (0x01) | nonce_12_bytes | ciphertext_||_tag |
```

- `version_byte` allows future algorithm migration (rotation to
  AES-256-SIV, ChaCha20-Poly1305, etc.).
- `nonce_12_bytes` is freshly random per encryption.
- `ciphertext_||_tag` is AES-256-GCM output (ciphertext + 16-byte
  authentication tag).

### §13.3 Decryption surface

The only code path that decrypts actor private keys is
`users.GetActorPrivateKey(ctx, userID)` returning `ed25519.PrivateKey`
in memory. Consumers MUST NOT log, print, or persist the decrypted
key. The reference implementation zeroes the byte slice in a
deferred call.

### §13.4 Key rotation (master key)

Master-key rotation is operator-driven and out of scope for v1.
The rotation procedure is documented separately when it ships
(Phase 1.22.K or sooner if operationally needed). The rotation
re-encrypts every row in the users table; the version byte in §13.2
allows the rotation to be staged.

## §14 Key rotation (actor keys)

> **Erratum E5 (2026-10-21).** This section covers actor signing keys,
> whose rotation is still deferred. Encryption keys are separate
> (§6.2) and rotate per ADR 0049, Decision 4 (§6.6).

**Deferred to Phase 1.22.K.** At v1, each actor has one keypair
for the life of the account. If a private key is compromised, the
operational answer is to delete the user account and re-register;
all federated references to the old actor URI become 404 and
remote peers will need to re-pair with the new actor.

This is ugly but contained. Acceptable for v1; the proper rotation
flow (rotation activity signed with the old key authorizing the
new key, recipient peers tracking key history during the rollover
window) is real protocol work that doesn't belong in 1.22.A.

The migration that adds the actor key columns includes a comment
noting the rotation deferral so it doesn't get forgotten.

## §16 Negotiated profiles

A **profile** is a named, frozen set of envelope members (and, where it
says so, activity types) layered on `protocol/v1`. It does not change
`@context` (§3.1), `object` stays a URI string (§3), and every other
rule of this document still applies.

### §16.1 Profile tokens

A profile is identified by a token of the form `<name>-<n>`: lowercase
letters, digits and hyphens, ending in a hyphen and a positive integer
(for example `archival-1`). The token is exchanged as a capability in
the handshake's `supported_capabilities` list (§11).

A published profile is frozen. Its member names, shapes, bounds, the
activity types it gates and its failure reasons never change. Any
change, including a new optional member, is a new token (for example
`archival-2`), negotiated separately.

### §16.2 When a profile is in effect

A profile is in effect between two peers only when its token is in the
capability intersection both peers stored when they paired (§11).

Advertising a token claims that the implementation both emits and
validates every member of that profile exactly as specified. An
implementation MUST NOT advertise a profile it does not fully enforce,
in both directions.

The intersection is computed at pairing. A pairing made before either
side supported a profile does not have it until the two instances
negotiate again (today, by re-pairing; a renegotiation path is
#1580's to define).

### §16.3 Sender and receiver rules

- A sender MUST NOT send a profile member, or an activity type the
  profile gates, to a peer whose stored intersection lacks the
  profile.
- When the profile marks a member REQUIRED for an activity (§17.1),
  the sender MUST refuse that recipient rather than send the activity
  without it: no envelope is sent, and the refusal is recorded. A
  sender MUST NOT strip profile members to fit a peer.
- A receiver MUST reject, with `profile_not_negotiated`, an envelope
  that carries a profile member or profile-gated type from a peer whose
  stored intersection lacks the profile. It is rejected before it is
  stored or applied.
- With the profile in effect, members are validated strictly, at every
  level (§3.2). A failure uses the profile's own reason
  (`archival_invalid` for archival-1).

### §16.4 Compatibility

A peer that does not implement a profile never advertises it, so the
profile is never in effect with that peer and it never receives the
profile's members. Senders MUST decide from the stored intersection,
never from whether the receiver would have rejected the members: a
receiver that does not yet enforce §3.2 (D2) would silently keep them.

## §17 Profile `archival-1`

> **Status:** specified 2026-11-17 (#1513), **not implemented** in the
> reference implementation (*Implementation status*, S1). Nothing
> advertises the token, and nothing sends or enforces these members yet.

`archival-1` carries what a receiving archive needs to preserve a
shared asset and prove that its files arrived intact: per-file fixity,
immutable versions, format identification, rights, persistent
identifiers, Dublin Core description, preservation events, deaccession
records and IIIF-aligned annotations. It uses the vocabularies archives
already use (OCFL, BagIt, PREMIS, IIIF, W3C Web Annotation, DCMI terms,
PRONOM, RightsStatements.org).

It does not make a receiver a preservation system. Virus scanning,
format identification, migration, access copies and storage stay local
to each instance; this profile defines how their results travel.

### §17.1 Members and where they appear

Each member is a top-level envelope member, like the type-specific
`aa:*` fields of §3. An envelope carries at most one of them. Under
encryption (§6.6) a member travels inside the ciphertext like any other
type-specific field.

| Member | Activity types | Required | Its `id` must equal |
|---|---|---|---|
| `aa:asset` | `Create`, `Update`, `aa:AssetVersion` of an `aa:Asset` | REQUIRED on `aa:AssetVersion`; a sender MUST include it on `Create` and `Update` of an asset | the envelope `object` |
| `aa:tombstone` | `Delete` of an `aa:Asset` | a sender MUST include it when deleting an asset | the envelope `object` |
| `aa:event` | `aa:Provenance` (§7.2) | REQUIRED | `object.asset` equals the envelope `object` |
| `aa:annotation` | `aa:Annotation` | REQUIRED | the canvas is on the `object`'s origin |

A member on any other activity type, or a second member, is
`archival_invalid`.

### §17.2 `aa:asset`

`aa:asset` describes the asset **record**. The bytes are CAS objects
(§8.5) identified by their SHA-256, and are listed in `files`. Two
assets may list the same bytes; a receiver keeps two records that share
one stored object.

| Field | Required | Value |
|---|---|---|
| `id` | yes | The asset URI (§8.2). |
| `version` | yes | §17.2.1. |
| `files` | yes | 1 to 256 entries, §17.2.2. |
| `sensitivity` | yes | `public`, `team`, `restricted` or `embargo`. A receiver applies it as the minimum tier and never lowers its own (§6.5). |
| `mature` | yes | Boolean. |
| `aiProvenance` | no | `none`, `assisted` or `generated` (ADR 0094). |
| `rights` | no | §17.2.5. |
| `requiredStatement` | no | §17.2.5. |
| `identifiers` | no | §17.2.5. |
| `accessionNumber` | no | Text, at most 256 bytes. |
| `description` | no | §17.2.6. |
| `iiifManifest` | no | §17.2.7. |

#### §17.2.1 Versions

`version` has `id` (a URI), `number` (an integer, 1 or more), `created`
(RFC 3339) and `predecessor`.

- Version numbers start at 1 and go up by one, as OCFL numbers its
  version directories. `predecessor` is null or absent on version 1 and
  is the previous version's `id` on every later version.
- A version is immutable once announced. Changed bytes always make a
  new version, linked to the one before it; a sender never sends a
  different file set under a version `id` it has already announced. An
  `Update` that changes only descriptive fields keeps the version.
- A receiver keeps every version it accepted and never replaces one in
  place.

#### §17.2.2 Files

Each entry of `files` has:

| Field | Required | Value |
|---|---|---|
| `role` | yes | `original` (the bytes as ingested), `preservation` (a copy kept for preservation) or `access` (a derivative for display). At least one `original` per version. |
| `contentUri` | yes | `cas://<sha256>` (§8.5), lowercase hex. |
| `checksums` | yes | §17.2.3. |
| `size` | yes | Integer bytes, 0 to 2^53 - 1. |
| `mediaType` | yes | The declared media type (RFC 6838 `type/subtype`, lowercase). A claim, not a verified format. |
| `identification` | no | §17.2.4. |
| `originalFilename` | no | The file's base name as it was received at ingest: at most 255 bytes of UTF-8, no `/` or `\`, not `.` or `..`, no control characters. Untrusted, and never a path. |

A file is listed only if the sender holds a verified SHA-256 for exactly
those bytes, equal to the hash in its `contentUri`. Bytes without a
recorded content hash are not listed at all and are never described as
fixity-checked. In the reference implementation that excludes today's
previews and other derivatives, whose storage rows carry no content hash
of their own; they can be listed once the variant-hash work records one.

#### §17.2.3 Checksums

`checksums` lists 1 to 3 `algorithm` / `value` pairs, at most one per
algorithm, as BagIt allows several manifests per bag. `value` is
lowercase hex.

- `sha256` is REQUIRED, and its value MUST equal the `contentUri` hash.
- `sha512` MAY be added.
- `md5` MAY be added only as additional legacy fixity (for example for
  holdings first bagged with MD5). It is never accepted on its own.

#### §17.2.4 Format identification

`identification` records a format identification: `puid`, a PRONOM
persistent unique identifier (`fmt/N` or `x-fmt/N`), and `tool`, the
`name` and `version` of the software that produced it. A PUID without
its tool is invalid. When the member is absent the file has not been
identified; `mediaType` alone never claims a verified format. A
receiver treats an identification as a claim and may identify the bytes
again.

#### §17.2.5 Rights and identifiers

- `rights` is a URI drawn from the Creative Commons licence URIs or the
  RightsStatements.org rights statement URIs, the same rule as the IIIF
  Presentation 3.0 `rights` property. Any other value is invalid.
- `requiredStatement` has `label` and `value`, each a language map: a
  BCP 47 language tag (or `none`) to a list of strings, as in IIIF.
- `identifiers` lists up to 16 persistent identifiers, each a `scheme`
  (`ark`, `doi`, `handle` or `local`) and a `value`.

A rights URI describes the rights in the content. It never grants a
peer permission to fetch or keep original bytes; that is #1573's
decision.

#### §17.2.6 Description

`description` is a subset of the DCMI Metadata Terms, as plain text:
`title`, `description`, `creator` (list), `subject` (list), `date` and
`language` (BCP 47). It is the baseline every archival-1 peer
understands, beneath any exchanged field schema (ADR 0083). Each list
holds at most 64 entries.

#### §17.2.7 IIIF manifest link

`iiifManifest` is the asset's IIIF Presentation 3.0 manifest URL on the
asset's own origin. It is data, not a fetch instruction: a receiver MUST
NOT fetch a manifest from any other origin, and fetching it at all is
governed by the share, like any other read of the object.

### §17.3 `aa:tombstone`: deaccession

`aa:tombstone` keeps the identity and fixity of a withdrawn asset, as
an ActivityStreams `Tombstone` keeps `formerType` and `deleted`.

| Field | Required | Value |
|---|---|---|
| `id` | yes | The asset URI. |
| `formerType` | yes | `aa:Asset`. |
| `deleted` | yes | RFC 3339. |
| `reason` | no | Text, at most 4096 bytes. |
| `lastVersion` | yes | The `id` of the last version. |
| `files` | yes | The last version's listed files, each `role`, `contentUri` and `checksums` (§17.2.3). |

A receiver withdraws future access according to its own policy and
keeps the tombstone, so a link to the asset resolves to a withdrawal
notice rather than an unexplained 404. A tombstone does not promise that
bytes already transferred are destroyed: nothing in this protocol can
recall data a peer has already received.

### §17.4 `aa:Provenance` and `aa:event`: preservation events

`aa:Provenance` carries one PREMIS 3 preservation event in `aa:event`.

| Field | Required | Value |
|---|---|---|
| `id` | yes | URI of the event. |
| `eventType` | yes | One of the tokens below. |
| `dateTime` | yes | RFC 3339. |
| `detail` | no | Text, at most 4096 bytes. |
| `outcome` | yes | `success`, `failure` or `warning`. |
| `outcomeDetail` | no | Text, at most 4096 bytes. |
| `object` | yes | `asset` (the asset URI, equal to the envelope `object`), optional `version` (a version `id`) and optional `contentUri` (a `cas://` URI). |
| `agents` | yes | 1 to 8 agents, each a `role` (`implementer`, `executing-program` or `authorizer`) and exactly one of `actor` (an actor URI) or `software` (`name` and `version`). |

Each `eventType` token stands for the term with the same label in the
Library of Congress *Preservation Events Controlled Vocabulary* (release
of 22 June 2017). The mapping is by label: the vocabulary gives an
`id.loc.gov/vocabulary/preservation/eventType` link for six of these
terms but none for format identification or transfer, so a token is not
a claim about an identifier URI.

| Token | PREMIS event type |
|---|---|
| `ingestion` | ingestion |
| `fixity-check` | fixity check |
| `format-identification` | format identification |
| `virus-check` | virus check |
| `migration` | migration |
| `replication` | replication |
| `transfer` | transfer |
| `deaccession` | deaccession |

A federated transfer is recorded on both sides: the sender records a
`transfer`, and the receiver records an `ingestion` and a
`fixity-check`, whose outcome is `failure` when §17.6 rejects a file.
ADR 0101 defines how these events form an asset's preservation
history; the activities ledger (ADR 0044) only carries them between
peers.

### §17.5 `aa:annotation`: W3C Web Annotation on an IIIF canvas

Under archival-1, `aa:Annotation` carries a W3C Web Annotation in
`aa:annotation`, replacing the earlier custom anchor descriptor, so a
shared annotation drops straight into an IIIF viewer.

- `type` is `Annotation`; `motivation` is `commenting`,
  `highlighting`, `describing` or `tagging`.
- `body` is a `TextualBody` with `format` `text/plain`, a `value` of
  at most 4096 bytes and an optional BCP 47 `language`.
- `target` has `source`, an IIIF canvas URI on the annotated asset's
  origin, and an optional `selector`: a `FragmentSelector` with
  `conformsTo` `http://www.w3.org/TR/media-frags/` and a `value` of
  either `xywh=x,y,w,h` (integer canvas pixels, width and height above
  zero) or `t=start` / `t=start,end` (seconds, end after start).
  Without a selector the annotation targets the whole canvas.

The selector is a deliberate subset of Media Fragments URI 1.0: plain
pixel `xywh` only (no `pixel:` or `percent:` unit), and plain seconds
for `t` (no `npt:` or SMPTE prefix, no open start such as `t=,20`). A
frozen subset keeps every archival-1 peer's parsing identical.

A receiver checks that a region lies inside the canvas when it applies
the annotation, using the canvas's real dimensions (#1578).

### §17.6 Fixity on arrival

Before a received file becomes visible, or counts as held, the receiver
MUST compute over the bytes it actually received:

- the length, reading at most `size` + 1 bytes, so an oversized stream
  is detected without reading it to the end;
- SHA-256, and every other algorithm the entry lists.

If the length differs from `size`, or any listed checksum differs, the
receiver MUST reject that file, and the activity that announced it, with
`fixity_mismatch`. It records a `fixity-check` event with outcome
`failure`, and it does not keep the bytes as the listed object.

A match proves the bytes are the ones the sender listed. It does not
prove the sender's other claims (format, rights, filename), which stay
claims, nor who sent them, which the envelope signature (§5) proves.

### §17.7 BagIt export mapping (informative)

A receiver that exports a shared collection as a BagIt bag (RFC 8493)
can map archival-1 directly:

- `data/original/`, `data/preservation/` and `data/access/` hold the
  files by role, named by `originalFilename` when present and safe on
  the target filesystem, otherwise by SHA-256;
- `manifest-sha256.txt` lists every payload file with its `sha256`;
  `manifest-sha512.txt` and `manifest-md5.txt` are added when those
  checksums were listed;
- `data/metadata/` holds the preservation events (§17.4), the
  description (§17.2.6) and the IIIF manifest;
- `bag-info.txt` carries `External-Identifier` (each identifier),
  `External-Description` (the description), `Bagging-Date` and
  `Payload-Oxum`;
- `tagmanifest-sha256.txt` covers the tag files.

Export is a local feature. This section fixes only the mapping.

### §17.8 What this profile does not do

- It does not authorise byte transfer. Whether a share permits a peer
  to fetch or keep original bytes is #1573, and the fetch is #72.
- It does not recall anything: versions and tombstones change what a
  receiver offers from then on, not what a peer already holds.
- It does not make sender claims trusted: a receiver verifies fixity
  itself (§17.6) and may re-identify formats.
- It is not implemented yet (S1), and the reference implementation does
  not advertise it.
