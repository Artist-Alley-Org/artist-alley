# Artist Alley federation protocol — v1

**Status:** in development (Phase 1.22)
**ADR:** [0043 — Federation walled-garden protocol](../../adr/0043-federation-walled-garden-protocol.md)
**Clean-room methodology:** [ADR 0040](../../adr/0040-clean-room-reverse-engineering-methodology.md)
**Approved sources:** [SOURCES.md](./SOURCES.md)
**Contributor register:** [CONTRIBUTORS.md](./CONTRIBUTORS.md)

This document is the **wire-format contract**. The Go implementation in
`app/internal/federation/` is one expression of this contract; a
re-implementer in any language must be able to interoperate using
only this document plus the conformance vectors at
`app/internal/federation/testdata/conformance/`.

When this document and the implementation drift, this document
wins, and the implementation is the bug.

## §1 Scope

The Artist Alley federation protocol is **ActivityPub-shaped** but
**artist-alley-to-artist-alley only at v1**. It is not Mastodon-
compatible. The parser rejects payloads carrying a non-artist-alley
`@context` value. The escape hatch to a future public-fediverse
translator is preserved by discipline (custom types map cleanly to
standard equivalents) but no translator ships at v1.

### §1.1 What this spec covers

- The on-the-wire envelope every activity uses (§3).
- The RFC 8785 canonicalization rules the envelope signature
  depends on (§4).
- The Ed25519 signature scheme (§5).
- The multi-recipient NaCl-box encryption envelope for restricted /
  embargo content (§6).
- The activity + object vocabulary, including the custom `aa:*`
  types (§7).
- The actor-identity URI shape and the immutability constraint that
  preserves cross-instance references (§8).
- The conformance-vector test pack every implementation validates
  against (§9).

### §1.2 What this spec does NOT cover (in v1)

- HTTP transport (inbox/outbox endpoints, delivery worker, retry
  policy). Spec'd separately in `v1-http.md` when Phase 1.22.D
  lands.
- Peer registry + handshake protocol. Phase 1.22.B.
- The `federation_shares` access-control layer. Phase 1.22.C.
- HTTP-Signatures algorithm details beyond the allowlist in §10.
  Full HTTP-Sig spec lands with 1.22.D.
- CAS fetch endpoint authorization. Phase 1.22.F.
- Key rotation. **Deferred to Phase 1.22.K.** v1 assumes one
  keypair per actor for life; rotation is operator-driven (re-issue
  identity, break federation references).
- Auto-sync policies. **Deferred to Phase 1.22.J.** v1 default is
  manual `aa:Share` for every shared object.

## §2 Notation

- Field names are JSON object keys, case-sensitive.
- Required fields are marked **REQUIRED**; optional fields **OPTIONAL**.
- The keyword **MUST** is RFC 2119.
- "Peer" means an Artist Alley instance the local instance has
  paired with via the handshake in §11 (1.22.B). "Actor" means a
  single user account, identified by §8's URI shape.

## §3 Envelope

Every activity is a JSON object matching this shape:

```jsonc
{
  "@context": "https://artist-alley.org/protocol/v1",   // REQUIRED, exact string match
  "type":     "aa:Approve",                              // REQUIRED, see §7
  "id":       "https://studio-a.example/activities/UUID", // REQUIRED, see §8
  "actor":    "https://studio-a.example/users/alice",    // REQUIRED, see §8
  "published":"2026-06-04T10:00:00Z",                    // REQUIRED, RFC 3339
  "to":       ["https://studio-b.example/users/bob"],    // OPTIONAL, array of actor URIs
  "cc":       [],                                        // OPTIONAL, array of actor URIs
  "object":   "https://studio-a.example/assets/UUID",    // CONDITIONAL; type-dependent
  "aa:*":     "...",                                     // type-specific fields, see §7
  "encrypted": { /* see §6 */ },                         // CONDITIONAL; mutually exclusive with plaintext body fields
  "signature": {                                         // REQUIRED unless 'encrypted' is present (then signature wraps the encrypted envelope)
    "type":      "Ed25519",                              // REQUIRED, exact string match (v1)
    "publicKey": "https://studio-a.example/users/alice#main-key", // REQUIRED
    "value":     "base64url-no-padding-signature-bytes"  // REQUIRED, see §5
  }
}
```

### §3.1 `@context` is a version string

`@context` MUST equal the exact string
`https://artist-alley.org/protocol/v1`. It is **not** a JSON-LD
context. The parser performs string equality, not LD context
resolution.

A payload with any other `@context` value MUST be rejected with
inbox status `invalid_context` (see §12).

### §3.2 Unknown fields are rejected, not ignored

Implementations MUST reject (not silently ignore) any top-level
field in an envelope, object, or `aa:*` extension that this
document does not define. Future additions to the vocabulary go
through versioning (`@context` → `protocol/v2`), not silent field
addition.

Rationale: silent unknown-field tolerance is the dominant cause of
fediverse interop bugs (each implementation invents its own
extensions, none can rely on the others honouring them). Rejecting
at the parser prevents Mastodon-style "Pleroma-only fields" drift
inside the walled garden.

### §3.3 Field ordering is irrelevant on the wire

JSON object key ordering on the wire does not change semantics.
Implementations MUST canonicalize (§4) before signing or verifying;
the canonical form has a defined ordering and the signature is
computed over the canonical bytes.

### §3.4 Empty arrays vs. omitted fields

`to: []` and an omitted `to` field are semantically equivalent
("the activity has no specifically-named direct recipients"). The
canonicalization in §4 normalizes both to "field omitted" so
signatures match.

## §4 Canonicalization (RFC 8785)

The signed payload (the input to §5's Ed25519 signature) is the
**JSON Canonicalization Scheme** (RFC 8785) representation of the
envelope **with the `signature` field removed**.

### §4.1 Algorithm

The full algorithm is defined in
[RFC 8785](https://datatracker.ietf.org/doc/html/rfc8785). The
salient rules:

1. **Object keys are sorted lexicographically by UTF-16 code unit.**
   (Not UTF-8; not Unicode normalized — UTF-16. RFC 8785 §3.2.3.)
2. **Numbers serialize as their shortest IEEE 754 double-precision
   round-trip representation** (RFC 8785 §3.2.2). `1.0` becomes `1`,
   `1.500` becomes `1.5`, `-0.0` becomes `0`, NaN and ±Infinity are
   forbidden in JSON entirely so this is moot.
3. **String escaping is minimal.** Only the six required JSON
   escapes (`"`, `\`, `\b`, `\f`, `\n`, `\r`, `\t`) and `\uXXXX`
   for the ASCII control range C0. All other code points serialize
   literally as UTF-8.
4. **No whitespace.** No indentation, no trailing newline, no
   separators beyond what the JSON grammar requires.
5. **Arrays preserve their input order.** Only object keys reorder.

### §4.2 Why these rules matter

Two JSON serializers that both produce "valid JSON" can produce
**different bytes** for the same logical object. Without RFC 8785,
a re-encoded envelope (e.g. one logged and replayed) might not
verify against its signature. The canonicalization is what makes
signatures portable across implementations and across storage
round-trips.

### §4.3 Removal of the `signature` field before canonicalization

The `signature` field is **deleted** from the JSON object before
canonicalization. Implementations MUST NOT canonicalize a
representation containing the signature and then "subtract" the
signature bytes after — that path admits subtle equality bugs.
Delete-then-canonicalize is the single correct order.

Pseudocode:

```
canonical_bytes = JCS(delete_key(envelope, "signature"))
signature       = Ed25519_Sign(actor_private_key, canonical_bytes)
envelope["signature"] = { type, publicKey, value: base64url(signature) }
```

### §4.4 RFC 8785 baseline conformance vectors

The IETF appendix examples (RFC 8785 Appendix B) are reproduced
verbatim in `testdata/conformance/rfc8785/*.json` as the baseline
canonicalization conformance pack. A re-implementer MUST validate
their canonicalizer against the RFC 8785 vectors **before** any
artist-alley-specific signature work. These vectors are public-
domain per IETF Trust Legal Provisions.

Each vector is the pair `{input.json, canonical.bin}` where
`canonical.bin` is the byte-for-byte RFC 8785 output. An
implementation's canonicalizer is correct iff it produces exactly
`canonical.bin` for `input.json`.

## §5 Signature (Ed25519)

### §5.1 Algorithm

Pure Ed25519 per [RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032).
The signing key is the actor's per-user Ed25519 private key,
generated at user creation (Phase 1.22.A) and stored encrypted at
rest per §13. The public key is published at the actor URI's
`#main-key` fragment (the value of `signature.publicKey` in §3).

### §5.2 Encoding

The 64-byte signature is encoded as **base64url-no-padding** (RFC
4648 §5, no `=` padding) and placed in `signature.value`.

The public key is published in PEM format
(`-----BEGIN PUBLIC KEY-----`...) per RFC 8410 at the actor's
`#main-key` URL. PEM is the wire format for human-tooling
compatibility (`openssl pkey -text`, etc.); the bytes inside are
the 32-byte raw Ed25519 public key.

### §5.3 Verify procedure

Given a received envelope `E` and the sender's published public key
`PK`:

```
sig_b64  = E["signature"]["value"]
sig_bytes = base64url_decode_no_padding(sig_b64)
if length(sig_bytes) != 64: REJECT  (sig_malformed)

E' = delete_key(E, "signature")
msg = JCS(E')
ok = Ed25519_Verify(PK, msg, sig_bytes)
if not ok: REJECT  (sig_invalid)
```

The `publicKey` field in the envelope is a URL hint about where to
fetch the public key; the receiver MUST have already obtained `PK`
through the handshake (§11) and the actor's actor-doc fetch. The
envelope's `publicKey` URL is matched against the actor's known
keys; a mismatch is `unknown_key`.

### §5.4 Key fingerprint

For audit + debugging, a key fingerprint is the lowercase hex
SHA-256 of the 32 raw public-key bytes (NOT the PEM wrapper).

### §5.5 Algorithm allowlist

`signature.type` MUST equal the exact string `"Ed25519"`. No other
algorithm is accepted at v1. A future protocol version may add
algorithms but each will require a new `@context` version string.

## §6 End-to-end encryption envelope (NaCl-box)

Activities targeting `restricted`- or `embargo`-tier objects (per
ADR 0020) optionally use a multi-recipient encryption envelope.
The plaintext fields are replaced with a single `encrypted` field;
the rest of the envelope (`@context`, `type`, `id`, `actor`,
`published`, `to`, `cc`, `signature`) remains in clear so the
inbox can authenticate the sender and dispatch the activity
without decrypting.

### §6.1 Shape

```jsonc
{
  "@context": "https://artist-alley.org/protocol/v1",
  "type":     "aa:Annotation",
  "id":       "https://studio-a.example/activities/UUID",
  "actor":    "https://studio-a.example/users/alice",
  "published":"2026-06-04T10:00:00Z",
  "to":       ["https://studio-b.example/users/bob",
               "https://studio-c.example/users/carol"],
  "encrypted": {
    "alg": "nacl-box",                                    // REQUIRED, exact match
    "ephemeralKey": "base64url-32-bytes-X25519-pubkey",   // REQUIRED
    "recipients": [
      {
        "actor": "https://studio-b.example/users/bob",
        "nonce": "base64url-24-bytes",                    // REQUIRED, per-recipient
        "ciphertext": "base64url-encrypted-payload-for-bob"
      },
      {
        "actor": "https://studio-c.example/users/carol",
        "nonce": "base64url-24-bytes",
        "ciphertext": "base64url-encrypted-payload-for-carol"
      }
    ]
  },
  "signature": { /* §5; signs the encrypted envelope, not the plaintext */ }
}
```

### §6.2 Distinct X25519 keypair per actor

NaCl-box uses **X25519** for key agreement. Each actor holds
**two independent keypairs**:

- An **Ed25519** keypair used for envelope signatures (§5).
- An **X25519** keypair used for NaCl-box recipient encryption.

Both public keys are published in the actor doc; both private
keys are stored encrypted-at-rest (§13).

**Why two keypairs instead of deriving X25519 from Ed25519.**
The Edwards-to-Montgomery birational map (RFC 7748 §4.1) does
permit deriving an X25519 public key from an Ed25519 public key,
and several deployed federation protocols do this. Artist Alley
v1 explicitly does NOT, for two reasons:

1. **Key-separation hygiene.** Reusing one keypair across two
   cryptographic primitives concentrates compromise: an attack
   against the signature scheme contaminates the encryption
   scheme and vice versa. Signal, Matrix, and every modern
   secure-messaging design publish distinct keys per primitive.
2. **Implementation simplicity + audit surface.** The field
   arithmetic for the birational map is security-sensitive
   (constant-time inversion in GF(2^255-19)) and adds either a
   third-party dependency or ~200 lines of in-tree crypto code we
   then have to maintain. Generating two keypairs at user-create
   time is one extra `curve25519.GenerateKey` call and 32 more
   bytes per user in the DB.

The 32-bytes-per-user storage cost and the small operational
cost of distributing two keys instead of one are accepted for v1.

### §6.3 Per-recipient encryption

For each recipient `R`:

1. The sender generates a single ephemeral X25519 keypair `(ek, EK)`
   used across all recipients in this envelope (saves bytes).
2. For each `R`: compute the NaCl-box ciphertext using:
   - sender's ephemeral X25519 secret `ek`
   - recipient's **published** X25519 public key (§6.2 — distinct
     from their Ed25519 signing key)
   - a fresh random 24-byte nonce, unique per recipient
   - the plaintext (JCS-canonicalized JSON of the type-specific
     fields the plain envelope would carry — `object`, `aa:comment`,
     etc.)

The recipient's decrypt is the reverse: ephemeral pub key from
`encrypted.ephemeralKey`, sender-known recipient X25519 secret,
nonce from `recipients[i].nonce`, ciphertext from
`recipients[i].ciphertext`. The plaintext is JCS-encoded JSON
which the recipient parses into the type-specific fields.

### §6.4 Verifying the signature with encryption present

The envelope's `signature` (§5) covers the **encrypted** envelope,
not the plaintext. This means:

- Any peer that holds the sender's Ed25519 public key can verify
  the activity came from the sender, even if they're not on the
  recipient list (they cannot decrypt, but they can authenticate).
- A recipient who decrypts MUST additionally validate the
  plaintext shape matches the expected `type` once decoded; a
  mismatch (sender signed `aa:Annotation` but plaintext decodes as
  `aa:Approve`) is `plaintext_type_mismatch` and is logged.

### §6.5 When encryption is mandatory

Per ADR 0043 §"Encryption tier":

- `public` and `team`-tier objects: plaintext envelope.
- `restricted`-tier objects: encryption envelope REQUIRED when
  delivering over a peer link whose `federation_peers.encryption_policy`
  is `e2e-encrypted`.
- `embargo`-tier objects: encryption envelope REQUIRED **always**,
  regardless of peer policy.

A `restricted`- or `embargo`-tier activity sent without an
encryption envelope to a peer whose policy demands one is
`encryption_required` and MUST be rejected by the recipient.

## §7 Vocabulary

### §7.1 Standard ActivityStreams activity types (carried through)

`Create`, `Update`, `Delete`, `Follow`, `Accept`, `Reject`, `Undo`,
`Like`, `Announce`, `Block`. Semantics follow
[ActivityStreams 2.0 Vocabulary](https://www.w3.org/TR/activitystreams-vocabulary/)
with the constraint that ALL of these MUST gate on a current
`federation_shares` row (or follow the same opt-in handshake in
the case of `Follow`).

| `aa:Unshare` | Revoke a previous `aa:Share`. | same as `aa:Share`'s target |
| `aa:Approve` | Federated approve action in a review workflow. | `aa:Asset` or `aa:Post` |

## §8 URI shape

### §8.1 Activity URIs

`https://{instance}/activities/{uuid}`

`{uuid}` MUST be UUID v4 in lowercase hex with hyphens (8-4-4-4-12).
The URI is the activity's `id` field.

### §8.2 Object URIs

`https://{instance}/{kind}/{uuid}`

`{kind}` MUST be one of: `posts`, `assets`, `collections`,
`workspaces`, `brand_kits`. Other kinds are reserved.

### §8.3 Actor URIs

`https://{instance}/users/{username}`

`{username}` is the user's stable handle. The actor URI is the
cross-instance identity for this user.

### §8.4 Username immutability

**Once a user account exists, the actor URI is the stable handle
for all cross-instance references.** Changing a user's username
breaks every federated reference to them (other peers' follow
graphs, share rows, audit-log actor pointers, prior activity
inboxes' actor_url fields).

The username-change admin surface (Phase 1.17.B-bis) MUST display
this consequence prominently. Once changed:

- Remote peers' inbound activities citing the old username 404.
- Remote followers' Follow rows no longer point at a live actor.
  The local user appears defederated to them until they re-follow.
- Local audit log entries naming the old username remain valid
  (the audit log is local truth).

This constraint matches Mastodon's policy and keeps the future
public-fediverse escape hatch intact. The alternative (UUID-keyed
actor URLs with username as a separate webfinger lookup) was
considered and rejected as more flexibility than v1 needs.

Display names are a SEPARATE field on the user profile and can
change freely without federation impact.

### §8.5 CAS URIs for asset bytes

`cas://<sha256>?content-type=<mime>&size=<bytes>`

`<sha256>` is lowercase hex of the SHA-256 of the asset bytes per
ADR 0008. Query parameters are advisory metadata; the SHA-256 is
the only authoritative identifier.

CAS URIs appear in `aa:Asset` and `aa:AssetVersion` activities as
the content reference. Resolution rule (per ADR 0043 §"CAS-native
federation"):

1. Check local storage; if present, use directly (no transfer).
2. Else issue a signed GET to
   `{origin_instance}/assets/{sha256}/bytes` (Phase 1.22.F endpoint).
3. Cache the bytes locally; future references dedup against the
   cache.

The CAS-fetch endpoint guards on `federation_shares` per fetch —
a peer requesting bytes for a hash they don't currently hold a
share for receives 403.

## §9 Conformance vectors

`app/internal/federation/testdata/conformance/` ships fixtures
every implementation validates against. Categories:

### §9.1 RFC 8785 canonicalization vectors

`testdata/conformance/rfc8785/`

Verbatim IETF appendix examples per §4.4. Each entry is a pair:

- `<name>.input.json` — input JSON
- `<name>.canonical.bin` — RFC 8785 canonical byte output

Implementations are correct iff their canonicalizer produces
`canonical.bin` for `input.json`.

### §9.2 Envelope round-trip vectors

`testdata/conformance/envelope/`

Each fixture:

```jsonc
{
  "description": "minimal aa:Approve, plaintext",
  "actor_keypair_hex": {
    "private": "...64 hex chars (32 bytes)...",
    "public":  "...64 hex chars (32 bytes)..."
  },
  "envelope_unsigned": { /* JSON object without signature */ },
  "canonical_bytes_b64": "...",
  "envelope_signed": { /* JSON object with signature applied */ },
  "expected_verify": true
}
```

An implementation:
1. Signs `envelope_unsigned` with `actor_keypair_hex.private` and
   compares the result against `envelope_signed.signature.value`.
   Bytes MUST match.
2. Independently canonicalizes `envelope_unsigned` and compares
   against `canonical_bytes_b64`. MUST match.
3. Verifies `envelope_signed` with `actor_keypair_hex.public` and
   confirms `expected_verify`.

### §9.3 Negative-path vectors

`testdata/conformance/reject/`

Each fixture is an envelope that MUST be rejected with a named
reason:

- `bad_context.json` — wrong `@context` value → `invalid_context`
- `missing_signature.json` — no `signature` field → `unsigned`
- `wrong_algorithm.json` — `signature.type` ≠ `"Ed25519"` →
  `unsupported_algorithm`
- `tampered_payload.json` — body changed after signing →
  `sig_invalid`
- `unknown_field.json` — unknown top-level key → `unknown_field`
- `bad_sig_length.json` — sig bytes ≠ 64 → `sig_malformed`

The conformance test pack walks each fixture and asserts the
parser rejects with the documented reason code.

### §9.4 NaCl-box envelope vectors

`testdata/conformance/nacl/`

Each fixture documents a sender keypair + N recipient keypairs +
an encrypted envelope. Implementations:

1. Decrypt as each recipient, recover plaintext, compare against
   expected.
2. Encrypt the same plaintext with the same ephemeral key (provided
   in the fixture for determinism) and confirm ciphertexts match.

## §10 HTTP transport (forward reference)

Full HTTP-Signatures spec lands with Phase 1.22.D. This section
locks two decisions now to prevent algorithm-confusion attacks
later:

### §10.1 Algorithm allowlist

Transport-layer HTTP-Signatures (the request-line signature on inbox
POSTs) accepts ONLY:

- `hs2019` with the `ed25519` key algorithm parameter

**Explicitly rejected:**

- RSA-PKCS1-v1_5, RSA-PSS, any RSA variant
- HMAC-SHA256 or any HMAC variant
- `rsa-sha256` (the legacy non-`hs2019` name)
- Any unspecified or future algorithm not in the allowlist above

Rationale: the historical fediverse HTTP-Sig deployment is RSA-
heavy; permitting RSA at our inbox creates a downgrade path. Locking
Ed25519-only matches our envelope signature scheme and keeps the key
material symmetric across both layers.

### §10.2 Signed headers (preliminary)

The inbox POST signature MUST cover at minimum:
`(request-target)`, `host`, `date`, `digest`. The `digest` header
is the SHA-256 digest of the request body, base64-encoded, prefixed
`SHA-256=`.

Replay window: 5 minutes. Requests with `date` skew beyond ±5
minutes from the receiver's clock are rejected (`stale_request`).

## §11 Peer handshake (forward reference)

Phase 1.22.B. The handshake establishes the two-way trust channel
described in ADR 0043 §"Trust model" — pairing creates the channel,
nothing else. Specified separately when 1.22.B lands.

For 1.22.A, the relevant constraint is: a peer's Ed25519
public key is established during handshake and stored in
`federation_peers.instance_public_key`. This key authenticates the
peer instance, distinct from the per-actor keys that sign envelopes.
Two layers of authentication, two distinct key spaces.

## §12 Status codes

Inbox + outbox dispatch results use a typed catalogue per ADR 0042.
Full enumerations live in `app/internal/federation/vocab.go`. The
ones referenced in this document:

### §12.1 Inbox rejection reasons

- `invalid_context` — `@context` field does not equal the
  protocol-v1 string.
- `unsigned` — envelope missing required `signature` field.
- `unsupported_algorithm` — `signature.type` not in the allowlist.
- `sig_malformed` — signature bytes wrong length or not decodable.
- `sig_invalid` — signature does not verify against the named key.
- `unknown_key` — `signature.publicKey` URL does not match any
  known key for the named actor.
- `unknown_field` — top-level field not in the spec.
- `unknown_actor` — `actor` URI does not resolve to a known actor.
- `unknown_peer` — sender's instance is not in `federation_peers`.
- `peer_disabled` — peer is in `federation_peers` but disabled.
- `unshared_object` — activity targets an object the sender does
  not hold a current `federation_shares` row for. (Phase 1.22.C
  is what enables this rejection; until then the inbox accepts.)
- `encryption_required` — plaintext envelope received for an
  object whose peer policy demands encryption.
- `plaintext_type_mismatch` — encrypted envelope decoded to a
  different `type` than the outer envelope declared.
- `stale_request` — HTTP-Sig date skew beyond replay window.
- `replay` — activity `id` already present in `federation_inbox`.

### §12.2 Outbox dispatch statuses

- `queued` — enqueued for delivery, not yet attempted.
- `sent` — delivered successfully.
- `failed` — delivery exhausted retries; will not be reattempted
  without manual intervention.
- `cancelled` — operator cancelled delivery (e.g. defederation
  before flush).

## §13 At-rest encryption of actor private keys

Per-user Ed25519 private keys MUST NOT be stored in plaintext at
rest. The user table stores `private_key_pem_encrypted` (BYTEA);
the bytes are AES-256-GCM ciphertext with the host master key.

### §13.1 Master key

The host master key is a 32-byte random key sourced from the
`AA_MASTER_KEY` environment variable (base64-encoded). It is
**not stored in the database**. It is operator-managed (mounted
secret, KMS, sealed-secret, whatever the deployment uses).

If `AA_MASTER_KEY` is missing or malformed at boot, the federation
package fails to initialize and any operation requiring an actor
private key returns an error. The rest of the application
proceeds; federation is the only feature gated on the master key
at v1.

### §13.2 Ciphertext format

```
| version_byte (0x01) | nonce_12_bytes | ciphertext_||_tag |
```

- `version_byte` allows future algorithm migration (rotation to
  AES-256-SIV, ChaCha20-Poly1305, etc.).
- `nonce_12_bytes` is freshly random per encryption.
- `ciphertext_||_tag` is AES-256-GCM output (ciphertext + 16-byte
  authentication tag).

### §13.3 Decryption surface

The only code path that decrypts actor private keys is
`users.GetActorPrivateKey(ctx, userID)` returning `ed25519.PrivateKey`
in memory. Consumers MUST NOT log, print, or persist the decrypted
key. The reference implementation zeroes the byte slice in a
deferred call.

### §13.4 Key rotation (master key)

Master-key rotation is operator-driven and out of scope for v1.
The rotation procedure is documented separately when it ships
(Phase 1.22.K or sooner if operationally needed). The rotation
re-encrypts every row in the users table; the version byte in §13.2
allows the rotation to be staged.

## §14 Key rotation (actor keys)

**Deferred to Phase 1.22.K.** At v1, each actor has one keypair
for the life of the account. If a private key is compromised, the
operational answer is to delete the user account and re-register;
all federated references to the old actor URI become 404 and
remote peers will need to re-pair with the new actor.

This is ugly but contained. Acceptable for v1; the proper rotation
flow (rotation activity signed with the old key authorizing the
new key, recipient peers tracking key history during the rollover
window) is real protocol work that doesn't belong in 1.22.A.

The migration that adds the actor key columns includes a comment
noting the rotation deferral so it doesn't get forgotten.
